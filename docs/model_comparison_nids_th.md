## 0. บทสรุปผู้บริหาร

โมเดลทั้ง 7 ตัวถูกเทรนและประเมินบนชุดข้อมูล CICIDS2017 แบบ **9 คลาส** ด้วยฟีเจอร์ระดับ flow **77 ฟีเจอร์** ใช้ข้อมูลเต็ม 2,497,980 แถว แบ่งชุดฝึกและชุดทดสอบ **ตามลำดับเวลา 70/30 ภายในแต่ละกลุ่ม (ไฟล์, คลาส)** ทุกโมเดลถูกปรับ hyperparameter ด้วยงบเท่ากัน และใช้วิธีจัดการ imbalance แบบเดียวกัน (`class_weight`)

**ข้อสรุปหลัก:** **CatBoost คือโมเดลที่แนะนำ** และชนะทั้งสามเกณฑ์การจัดอันดับที่กำหนดไว้ล่วงหน้า ได้แก่ Overall (macro-F1 สูงสุด 0.8873), Security (recall_macro สูงสุด 0.8970 ภายใต้ FPR ≤ 1%) และ Deployment (p95 latency ต่ำสุด 8.39 ms ต่อ 1,000 flow ในกลุ่มที่ macro-F1 ห่างจากอันดับหนึ่งไม่เกิน 0.02) CatBoost ยังพลาดการโจมตีน้อยที่สุด (2,049 flow จาก 127,721) และมีไฟล์โมเดลเพียง 2.5 MB

**ข้อค้นพบ 5 ข้อที่สำคัญกว่าตารางอันดับ:**

1. **กลุ่ม boosting สามตัวแรกใกล้กันมาก** — CatBoost 0.8873, LightGBM 0.8774, XGBoost 0.8773 เมื่อนับเฉพาะ 7 คลาสที่มีตัวอย่างทดสอบ ≥ 30 แถว (`f1_macro_reportable`) LightGBM นำเล็กน้อยที่ 0.8627 เทียบกับ 0.8613 ของ CatBoost คุณภาพการทำนายจึงใกล้เคียงกัน ที่ทำให้ CatBoost ชนะคือเกณฑ์รอง ได้แก่ พลาดการโจมตีน้อยกว่าราว 3 เท่า (2,049 เทียบกับ 5,483–6,220) และเร็วกว่า 6–17 เท่า
2. **Bot คือคลาสที่ยากที่สุดของทุกโมเดล** — recall อยู่ที่ 0.15–0.16 ในทั้ง 7 โมเดล เพราะการแบ่งตามเวลาทำให้ Bot ช่วงท้ายที่อยู่ในชุดทดสอบต่างจากช่วงต้นที่ใช้ฝึก นี่คือผลของ distribution shift ภายใน capture ไม่ใช่จุดอ่อนของโมเดลใดโมเดลหนึ่ง (หัวข้อ 4.3)
3. **LightGBM และ XGBoost ให้ false positive ต่ำที่สุด** — FPR 0.022% และ 0.038% เทียบกับ 0.065% ของ CatBoost ถ้าองค์กรให้ความสำคัญกับจำนวน alert ผิดมากกว่าจำนวนการโจมตีที่หลุด สองตัวนี้คือทางเลือก แต่แลกกับการพลาดการโจมตีมากขึ้นราว 3 เท่า
4. **Stacking แย่กว่าโมเดลฐานของตัวเอง** — macro-F1 0.6822 ต่ำกว่า LightGBM, XGBoost และ Random Forest ที่เป็นโมเดลฐาน สาเหตุหลักคือทำนาย BENIGN เป็น Brute Force จำนวนมาก (precision ของ Brute Force เพียง 0.108) และใช้เวลาเทรนนานที่สุด (2,755 วินาที)
5. **Accuracy ยังทำให้เข้าใจผิด** — baseline "ทาย BENIGN เสมอ" ได้ accuracy 0.8296 แล้ว MLP ได้ accuracy 0.9331 แต่ macro-F1 เพียง 0.5369 และพลาดการโจมตี 19,677 flow การตัดสินจึงใช้ macro-F1, recall รายคลาส และ FPR เป็นหลัก

### 3.1 Logistic Regression

**เอกสารทางการ:** https://scikit-learn.org/stable/modules/linear_model.html#logistic-regression
**งานวิจัยต้นฉบับ:** Cox, D. R. (1958) *JRSS-B* 20(2):215–242 · McFadden, D. (1974) — ส่วนขยาย multinomial/softmax · Liu & Nocedal (1989) *Mathematical Programming* 45:503–528 — solver `lbfgs`

**อัลกอริทึมพื้นฐาน** — จำลองความน่าจะเป็นของคลาสด้วย softmax บนคะแนนเชิงเส้น `P(y=k|x) = exp(wₖᵀx+bₖ) / Σⱼ exp(wⱼᵀx+bⱼ)` หาค่าพารามิเตอร์ด้วยการลด cross-entropy ที่มี L2 penalty ซึ่งเป็นฟังก์ชัน convex จึงมีจุดเหมาะที่สุดแบบ global เพียงจุดเดียว · **พารามิเตอร์ที่ปรับได้:** `C=300, tol=1e-4, fit_intercept=True`

**จุดแข็ง**
- เป็นโมเดลเดียวในชุดที่ **มีคำตอบ global optimum เพียงคำตอบเดียว** เทรนซ้ำได้ผลเหมือนเดิม
- ค่าสัมประสิทธิ์ตีความได้โดยตรงเป็น log-odds ต่อหนึ่งหน่วยของฟีเจอร์ที่ standardize แล้ว — **ตีความง่ายที่สุดในชุด**
- **เร็วที่สุดที่วัดได้:** p95 5.15 ms ต่อ 1,000 flow (232,391 flows/s) และไฟล์โมเดลเล็กจนปัดเป็น 0.0 MB
- recall รวมของการโจมตีสูงถึง 0.9746 และ recall ของ DDoS 0.9979, PortScan 0.9941

**จุดอ่อน (วัดได้)**
- เส้นแบ่งเป็นเชิงเส้นเท่านั้น จึงจับปฏิสัมพันธ์ระหว่างฟีเจอร์ไม่ได้ หากไม่สร้าง interaction term เอง
- **FPR 16.93%** หรือ alert ผิด 105,258 รายการบนชุดทดสอบ — ต้นทุนของการได้ recall สูงด้วยเส้นแบ่งเชิงเส้น
- macro-F1 0.5574 และ precision ต่ำมากในคลาสหายาก (Bot 0.0012, Infiltration 0.0008, Web Attack 0.0499)
- เวลาเทรน 653.7 วินาที นานกว่าที่คาดสำหรับโมเดลเชิงเส้น เพราะ `C=300` ทำให้ regularization อ่อนและ L-BFGS ต้องใช้หลายรอบกว่าจะ converge บนข้อมูล 1.7 ล้านแถว

**ความซับซ้อนเชิงคำนวณ** — เทรน `O(i · n · d · K)` โดย i คือจำนวนรอบ L-BFGS · ทำนาย `O(d · K)` = 77 × 9 = 693 การคูณ-บวกต่อ flow

**การตีความ** — ดีที่สุด SHAP ของโมเดลเชิงเส้นลดรูปเป็น `φᵢ = wᵢ(xᵢ − E[xᵢ])` ซึ่งแม่นยำและคำนวณได้ในเวลาเท่ากับการทำนาย

**ความทนทานต่อฟีเจอร์ที่ไม่ scale** — แย่มากกับข้อมูลดิบ เพราะ `Flow Duration` (ช่วง ~10⁸) จะกลบฟีเจอร์ช่วงเล็ก ต้องใช้ `StandardScaler` เสมอ

**ความเหมาะสมกับ class imbalance** — `class_weight` ช่วยดัน recall ขึ้น แต่ด้วยเส้นแบ่งเชิงเส้นจึงแลกมาด้วย false positive จำนวนมาก

**การใช้งานใน SOC** — ไม่เหมาะเป็นตัวตรวจจับหลัก · บทบาทที่เหมาะสม: (ก) **baseline โปร่งใส** ที่บอกว่าปัญหานี้ต้องการความไม่เชิงเส้นมากแค่ไหน (ข) **meta-learner ใน stacking ensemble** ตามที่ใช้จริงใน `src/models/stacking.py` (ค) ตัวตัดสินที่ตรวจสอบย้อนกลับได้ในสภาพแวดล้อมที่มีข้อกำหนดด้าน compliance

### 3.2 Random Forest

**เอกสารทางการ:** https://scikit-learn.org/stable/modules/ensemble.html#random-forests
**งานวิจัยต้นฉบับ:** **Breiman, L. (2001) "Random Forests" *Machine Learning* 45(1):5–32** · Breiman (1996) Bagging · Ho (1995) Random Subspace · Louppe (2014) วิทยานิพนธ์ที่วิเคราะห์ implementation ของ sklearn

**อัลกอริทึมพื้นฐาน** — ensemble แบบ bagging ของ decision tree ที่สุ่มสองชั้น: แต่ละต้นเทรนบน bootstrap sample และแต่ละจุดแตกกิ่งพิจารณาเฉพาะฟีเจอร์ย่อยแบบสุ่ม (√77 ≈ 9) การเฉลี่ยต้นไม้ที่มีความแปรปรวนสูงแต่ไม่สัมพันธ์กันช่วยลดความแปรปรวนรวมโดย bias ไม่เปลี่ยน · **พารามิเตอร์ที่ปรับได้:** `n_estimators=300, max_depth=30, min_samples_split=2, min_samples_leaf=1`

**จุดแข็ง**
- **Web Attack F1 สูงสุดในการศึกษา (0.9500)** และ precision ของ Web Attack 0.9866
- **CV แคบที่สุดในการศึกษา (σ = 0.0135)**
- ไม่ขึ้นกับ scale ของข้อมูล ใช้ output ดิบจาก CICFlowMeter ได้ทันที
- ขนานได้เกือบสมบูรณ์ และให้ out-of-bag error เป็นการประมาณ generalization error โดยไม่ต้องกันข้อมูลไว้

**จุดอ่อน (วัดได้)**
- **ไฟล์โมเดลใหญ่ที่สุดในการศึกษา (124.5 MB)** — 300 ต้น ลึกได้ถึง 30 บนข้อมูล 1.7 ล้านแถว
- **p95 latency 104.12 ms ต่อ 1,000 flow** ช้ากว่า CatBoost 12 เท่า เพราะการเดินต้นไม้ 300 ต้นคือการไล่ pointer ที่ cache locality แย่
- macro-F1 0.8404 อันดับสี่ และพลาดการโจมตี 9,232 flow มากเป็นอันดับสอง · DoS recall เพียง 0.8372
- Bot F1 เพียง 0.0459 แย่กว่ากลุ่ม boosting ชัดเจน
- extrapolate เกินช่วงข้อมูลที่เทรนไม่ได้ และ feature importance แบบ impurity มีอคติเข้าข้างฟีเจอร์ cardinality สูง (Strobl et al. 2007) ควรใช้ SHAP แทน

**ความซับซ้อนเชิงคำนวณ** — เทรน `O(T · √d · n log²n)` · ทำนาย `O(T · depth)` = 300 × สูงสุด 30 การเปรียบเทียบต่อ flow บวกกับ cache miss จำนวนมาก

**หน่วยความจำและ scalability** — หน่วยความจำตอน deploy คือข้อจำกัดหลัก · บรรเทาได้ด้วยการจำกัด `max_depth`, ตั้ง `min_samples_leaf ≥ 5` หรือ compile ผ่าน Treelite/ONNX Runtime

**ความอ่อนไหวของ hyperparameter** — น้อยที่สุดในกลุ่มต้นไม้ ค่า default ดีอยู่แล้ว และการเพิ่ม `n_estimators` ปลอดภัยเสมอ

**การตีความ** — ดี TreeSHAP ใช้ได้อย่างแม่นยำที่ความซับซ้อน `O(T · L · D²)` (Lundberg et al. 2020)

**ความทนทานต่อ noise** — ดี การเฉลี่ยแบบ bagging ช่วยกลบ label noise ซึ่งสำคัญกับ CICIDS2017 ที่ติด label ตาม *ช่วงเวลาการโจมตี* (Engelen et al. 2021)

**การใช้งานใน SOC** — เหมาะกับงานให้คะแนนแบบ batch แต่ขนาดและ latency ไม่เหมาะกับเส้นทาง inline หากไม่ compile ก่อน · บทบาทที่เหมาะสม: **ตัวตรวจสอบเฉพาะ Web Attack** ที่ได้ทั้ง F1 และ precision สูงสุด

### 3.3 XGBoost

**เอกสารทางการ:** https://xgboost.readthedocs.io/
**งานวิจัยต้นฉบับ:** **Chen, T. & Guestrin, C. (2016) "XGBoost: A Scalable Tree Boosting System" *KDD '16* 785–794** · Friedman (2001) *Annals of Statistics* 29(5):1189–1232 — รากฐาน gradient boosting · Friedman (2002) — stochastic subsampling

**อัลกอริทึมพื้นฐาน** — boosting แบบเพิ่มทีละขั้นบน **การกระจาย Taylor อันดับสอง** ของ loss ต้นไม้ใหม่แต่ละต้นเรียนรู้ทั้ง gradient และ Hessian ของ residual ให้ค่าน้ำหนัก leaf ที่เหมาะที่สุดในรูปปิด `w* = −G/(H+λ)` และค่า gain ของการแตกกิ่ง `½[G_L²/(H_L+λ) + G_R²/(H_R+λ) − G²/(H+λ)] − γ` โดย regularization ถูกเขียนไว้ใน objective · **พารามิเตอร์ที่ปรับได้:** `n_estimators=800, max_depth=10, learning_rate=0.05, subsample=0.8`, `tree_method='hist'` (GPU)

**จุดแข็ง**
- **Brute Force F1 สูงสุด (0.9993)** และ macro-F1 0.8773 แทบเท่ากับ LightGBM
- **FPR ต่ำเป็นอันดับสอง (0.038%)** alert ผิด 236 รายการบนชุดทดสอบ
- **CV mean สูงที่สุด (0.9697)** บนชุดฝึก
- มี regularization ที่ชัดเจน (`λ`, `γ`, `α`) พร้อม row/column subsampling
- รองรับข้อมูลว่างโดยกำเนิด (sparsity-aware split finding) ซึ่งตรงกับ `Flow Bytes/s` และ `Flow Packets/s` ที่ให้ค่า Inf/NaN บน flow ที่ duration เป็นศูนย์
- ระบบนิเวศพร้อมใช้งานจริง: ONNX export, Treelite, GPU inference และ binding สำหรับ JVM/C++

**จุดอ่อน (วัดได้)**
- **พลาดการโจมตี 5,483 flow** มากกว่า CatBoost 2.7 เท่า · DoS recall 0.8937 เทียบกับ 0.9571 ของ CatBoost
- **p95 latency 54.10 ms ต่อ 1,000 flow** ช้ากว่า CatBoost 6.5 เท่า · multiclass สร้างต้นไม้ `n_estimators × K` = 800 × 9 = 7,200 ต้น ที่ลึกได้ถึง 10
- ไฟล์โมเดล 15.8 MB ใหญ่กว่า CatBoost 6 เท่า
- มี hyperparameter ที่สัมพันธ์กันหลายตัว พื้นที่ปรับจูนกว้าง

**ความซับซ้อนเชิงคำนวณ** — เทรน (`hist`): `O(T · K · (n · d + b · d))` โดย b คือจำนวน histogram bin · ทำนาย: `O(T · K · depth)` = 800 × 9 × 10 = 72,000 การเปรียบเทียบต่อ flow

**ความอ่อนไหวของ hyperparameter** — สูง ปฏิสัมพันธ์สำคัญคือ `max_depth` × `learning_rate` × `n_estimators` · overfit ได้ง่ายหากเพิ่ม `max_depth` โดยไม่ลด `learning_rate`

**การตีความ** — ยอดเยี่ยม TreeSHAP แม่นยำและเร็ว เพราะพัฒนาร่วมกับ XGBoost (Lundberg et al. 2020) ให้ทั้ง gain/cover/weight importance, SHAP interaction values และ attribution รายการทำนาย

**ความทนทานต่อ noise** — ไม่ขึ้นกับ scale และรองรับ NaN/Inf โดยกำเนิด · ทนต่อ label noise ได้น้อยกว่า Random Forest เพราะ boosting เพิ่มน้ำหนักให้ตัวอย่างที่ทายผิด บรรเทาด้วย `subsample < 1.0`

**การใช้งานใน SOC** — ทางเลือกที่ดีเมื่อ **FPR ต่ำสำคัญกว่าจำนวนการโจมตีที่หลุด** และมี toolchain สำหรับ compile (Treelite/ONNX) เพื่อลด latency · เป็นตัวเลือกอันดับสองรองจาก CatBoost

### 3.4 LightGBM

**เอกสารทางการ:** https://lightgbm.readthedocs.io/
**งานวิจัยต้นฉบับ:** **Ke, G. et al. (2017) "LightGBM: A Highly Efficient Gradient Boosting Decision Tree" *NeurIPS 30* 3146–3154** · Fisher (1958) *JASA* 53(284):789–798 — การแบ่งกลุ่ม categorical ที่เหมาะที่สุด

**อัลกอริทึมพื้นฐาน** — GBDT แบบ histogram ที่มีกลไกเด่น 3 อย่าง: (1) **การเติบโตแบบ leaf-wise** แตกกิ่งที่ leaf ซึ่งลด loss ได้มากที่สุดเสมอ (2) **GOSS** เก็บตัวอย่างที่มี gradient สูงไว้ทั้งหมด และสุ่มเลือกตัวอย่าง gradient ต่ำพร้อมชดเชยน้ำหนัก (3) **EFB** รวมฟีเจอร์เบาบางที่ไม่ทับซ้อนกันเป็นฟีเจอร์เดียว · **พารามิเตอร์ที่ปรับได้:** `n_estimators=1000, num_leaves=127, min_child_samples=1, learning_rate=0.1`

**จุดแข็ง**
- **FPR ต่ำที่สุดในการศึกษา (0.022%)** alert ผิดเพียง 136 รายการ และ binary precision สูงสุด 0.9989
- **`f1_macro_reportable` สูงสุด (0.8627)** นำ CatBoost 0.0014
- DDoS และ PortScan F1 สูงสุด (0.9995, 0.9832) และ Bot F1 สูงสุดในบรรดาโมเดลทั้งหมด (0.2514) แม้ยังต่ำ
- histogram binning ให้การแตกกิ่งที่ `O(n)` และใช้หน่วยความจำตอนเทรนน้อย

**จุดอ่อน (วัดได้)**
- **p95 latency ช้าที่สุดในการศึกษา (144.02 ms ต่อ 1,000 flow)** เพราะ 1,000 รอบ × 9 คลาส × สูงสุด 127 leaf
- ไฟล์โมเดล 54.9 MB และพลาดการโจมตี 6,220 flow มากกว่า CatBoost 3 เท่า · DoS recall 0.8891
- **ค่า `min_child_samples=1` ยังเป็นความเสี่ยง** ใน run เก่าค่านี้ร่วมกับการ oversample Infiltration ทำให้โมเดลท่องจำแถวที่ซ้ำและล้มเหลว (accuracy 0.7634) ใน run นี้ใช้ `class_weight` แทน oversample จึงไม่เกิดปัญหา แต่ถ้ากลับไปใช้ oversample ต้องจำกัด `min_child_samples` ให้สูงขึ้น (หัวข้อ 5.2)

**ความซับซ้อนเชิงคำนวณ** — เทรน `O(T · K · n' · d')` โดย n' < n จาก GOSS และ d' < d จาก EFB · ทำนาย `O(T · K · depth)` แต่ต้นไม้แบบ leaf-wise ลึกและไม่สมมาตร

**ความอ่อนไหวของ hyperparameter** — สูงที่สุดในกลุ่ม boosting พารามิเตอร์อันตรายคือ `num_leaves` และ `min_child_samples` ซึ่งส่งผลคูณกัน · เอกสารของ LightGBM แนะนำให้ `num_leaves < 2^max_depth` และตั้ง `min_child_samples` ในหลักร้อยสำหรับข้อมูลขนาดนี้

**การตีความ** — TreeSHAP ใช้ได้แม่นยำ แต่ต้นไม้ leaf-wise ที่ลึกและไม่สมมาตรทำให้การตรวจดูต้นไม้รายต้นไม่ค่อยมีประโยชน์

**ความทนทานต่อ noise** — ไม่ขึ้นกับ scale และรับ NaN ได้ แต่การโตแบบ leaf-wise มุ่งไปยังบริเวณที่ loss สูง ซึ่งเป็นที่อยู่ของ flow ที่ติด label ผิด จึงทนต่อ label noise ได้น้อยกว่าโมเดลอื่นในกลุ่ม

**การใช้งานใน SOC** — ทางเลือกที่ดีที่สุดเมื่อ **จำนวน alert ผิดคือข้อจำกัดหลัก** และเส้นทางไม่ต้องการ latency ต่ำ เช่น การให้คะแนนแบบ batch หรือคิวตรวจสอบรอง

### 3.5 CatBoost — ⭐ โมเดลที่แนะนำ

**เอกสารทางการ:** https://catboost.ai/docs/
**งานวิจัยต้นฉบับ:** **Prokhorenkova, L. et al. (2018) "CatBoost: unbiased boosting with categorical features" *NeurIPS 31* 6638–6648** · Dorogush, Ershov & Gulin (2018) arXiv:1810.11363

**อัลกอริทึมพื้นฐาน** — gradient boosting ที่มีกลไกเด่นสองอย่าง: (1) **Ordered boosting** คำนวณ residual ของแต่ละตัวอย่างจากโมเดลที่เทรนด้วยตัวอย่างที่มาก่อนหน้าเท่านั้น จึงกำจัด *prediction shift* ที่ทำให้ boosting ทั่วไปมีอคติ (2) **Oblivious (symmetric) trees** ทุก node ในระดับเดียวกันใช้เงื่อนไขแตกกิ่งเดียวกัน ต้นไม้ลึก 6 จึงอธิบายได้ด้วยคู่ (ฟีเจอร์, threshold) เพียง 6 คู่ และการทำนายกลายเป็นการคำนวณ index 6 บิตเข้าตาราง 64 ช่อง · **พารามิเตอร์ที่ปรับได้:** `iterations=500, depth=6, learning_rate=0.15, l2_leaf_reg=1` (GPU)

**จุดแข็ง (วัดได้)**
- **ชนะทั้งสามเกณฑ์การจัดอันดับ:** macro-F1 สูงสุด (0.8873), recall_macro สูงสุดภายใต้ FPR ≤ 1% (0.8970) และ p95 latency ต่ำสุดในกลุ่มที่ macro-F1 ใกล้อันดับหนึ่ง (8.39 ms)
- **พลาดการโจมตีน้อยที่สุด (2,049 flow, FNR 1.60%)** และ detection rate สูงสุด 0.9840
- **DoS F1 สูงสุด (0.9769) และ DoS recall 0.9571** เทียบกับ 0.84–0.89 ของต้นไม้ตัวอื่น ซึ่งเป็นเหตุผลหลักที่พลาดการโจมตีน้อยกว่า เพราะ DoS เป็นคลาสโจมตีที่ใหญ่ที่สุดในชุดทดสอบ
- **accuracy, balanced accuracy, weighted-F1 และ MCC สูงสุด** (0.9953, 0.8970, 0.9952, 0.9844)
- **ทำนายเร็วที่สุดในกลุ่มต้นไม้:** p95 8.39 ms ต่อ 1,000 flow (131,975 flows/s) เพราะ oblivious tree เปลี่ยนการเดินต้นไม้ให้เป็นการคำนวณ index ที่ไม่มี branch และ vectorize ได้
- **ไฟล์โมเดลเล็กที่สุดในกลุ่มต้นไม้ (2.5 MB)** เล็กกว่า Random Forest 50 เท่า
- เทรนเร็วที่สุดที่วัดได้ (44.6 วินาทีบน GPU)

**จุดอ่อน**
- FPR 0.065% สูงกว่า LightGBM 3 เท่าและ XGBoost 1.7 เท่า (alert ผิด 404 เทียบกับ 136 และ 236)
- CV σ = 0.0225 กว้างกว่ากลุ่มต้นไม้ตัวอื่น
- `f1_macro_reportable` (0.8613) ตามหลัง LightGBM เล็กน้อย ข้อได้เปรียบด้านคุณภาพการทำนายจึงขึ้นกับ DoS และคลาสหายาก
- oblivious tree แสดงความสัมพันธ์ได้น้อยกว่าต่อหนึ่งต้น ต้องใช้ต้นไม้มากกว่าเพื่อให้เทียบเท่าโครงสร้างอิสระ
- จุดเด่นด้านฟีเจอร์ categorical ไม่ได้ถูกใช้ เพราะทั้ง 77 ฟีเจอร์เป็นตัวเลข

**ความซับซ้อนเชิงคำนวณ** — เทรน `O(T · K · n · d)` โดยมีค่าคงที่เพิ่มตามจำนวน permutation · ทำนาย `O(T · depth)` = 500 × 6 = 3,000 การดำเนินการแบบไม่มี branch และ vectorize ได้

**ความอ่อนไหวของ hyperparameter** — น้อยที่สุดในสาม boosting library ordered boosting ทำให้ความเสี่ยง overfitting ต่ำ

**การตีความ** — ดีมาก TreeSHAP ใช้ได้ และ oblivious tree อ่านง่าย เพราะต้นไม้ลึก 6 คือกฎเพียง 6 ข้อ · ผล SHAP ของโมเดลนี้มีในเล่มรายงานหัวข้อ 4.1.4 และใน `results/cicids2017_temporal_v1_shap/` (คุณลักษณะสำคัญที่สุดคือ Destination Port, Init_Win_bytes_forward และ Init_Win_bytes_backward)

**ความทนทานต่อ noise** — ไม่ขึ้นกับ scale · ordered boosting ให้การป้องกันเชิงหลักการต่ออคติ prediction shift ที่เกิดจาก label noise

**ความเหมาะสมกับ class imbalance** — แข็งแกร่ง ได้ balanced accuracy สูงสุด (0.8970) ด้วย `class_weight` เดียวกับโมเดลอื่น

**การใช้งานใน SOC** — **ตัวตรวจจับหลักแบบ inline** ด้วย latency ต่ำ ไฟล์เล็ก ไม่ต้อง compile และพลาดการโจมตีน้อยที่สุด · ข้อแลกเปลี่ยนเดียวคือ alert ผิดมากกว่า LightGBM/XGBoost เล็กน้อย ซึ่งจัดการได้ด้วยการรวมกลุ่ม alert (หัวข้อ 6.2)

### 3.6 Multi-Layer Perceptron (MLP)

**เอกสารทางการ:** https://scikit-learn.org/stable/modules/neural_networks_supervised.html
**งานวิจัยต้นฉบับ:** **Rumelhart, Hinton & Williams (1986) *Nature* 323:533–536** · Cybenko (1989) และ Hornik (1991) — universal approximation · Kingma & Ba (2015) *ICLR* — optimizer Adam · **Grinsztajn, Oyallon & Varoquaux (2022) *NeurIPS D&B*** — อธิบายว่าทำไมต้นไม้ยังชนะโครงข่ายประสาทบนข้อมูลตาราง

**อัลกอริทึมพื้นฐาน** — โครงข่ายประสาทเทียมแบบ feedforward ที่เชื่อมต่อเต็มรูปแบบ ใช้ ReLU และ softmax เทรนด้วย backpropagation กับ Adam · **พารามิเตอร์ที่ปรับได้:** `hidden_layer_sizes=(256, 128, 64, 32), learning_rate_init=0.0005, batch_size=256, alpha=0.0001` คือ 77 → 256 → 128 → 64 → 32 → 9

**จุดแข็ง**
- เป็น universal function approximator แทนเส้นแบ่งเรียบเอียงที่ต้นไม้ต้องประมาณด้วยรูปขั้นบันได
- **ไฟล์โมเดลเล็ก (0.7 MB)** และ **latency คงที่** p95 12.50 ms ต่อ 1,000 flow เพราะการทำนายคือการคูณเมทริกซ์ลำดับตายตัว
- รองรับการเรียนรู้แบบ incremental ผ่าน `partial_fit` เป็นโมเดลเดียวในชุดที่อัปเดตแบบ online ได้

**จุดอ่อน (วัดได้)**
- **macro-F1 ต่ำที่สุด (0.5369)** และ balanced accuracy ต่ำที่สุด (0.7112)
- **พลาดการโจมตีมากที่สุด (19,677 flow, FNR 15.4%)** · DoS recall เพียง 0.6583 และ Heartbleed recall 0
- CV แปรปรวนมากที่สุด (σ = 0.0538) เพราะ objective ไม่ convex
- **`MLPClassifier` ของ sklearn ไม่มีพารามิเตอร์ `class_weight`** วิธีจัดการ imbalance มาตรฐานจึงใช้ไม่ได้ เป็นเหตุผลเชิงโครงสร้างที่คลาสหายากแย่
- ต้อง scale ฟีเจอร์อย่างเคร่งครัด และตีความได้แย่ที่สุด ต้องใช้ KernelSHAP ที่เป็นการประมาณ
- Grinsztajn et al. (2022) ระบุว่าโครงข่ายประสาทมี inductive bias แบบ rotationally invariant ซึ่งไม่เข้ากับข้อมูลตารางที่แต่ละฟีเจอร์มีความหมายเฉพาะตัว

**ความซับซ้อนเชิงคำนวณ** — ทำนายด้วย FLOPs คงที่ต่อ flow ไม่มี branch ที่ขึ้นกับข้อมูล · เทรนเชิงเส้นกับจำนวนรอบและตัวอย่าง (818.7 วินาทีบน CPU)

**การใช้งานใน SOC** — ไม่แนะนำเป็นตัวตรวจจับหลัก · บทบาทที่เหมาะสม: **ตัวเฝ้าระวัง drift แบบ online** ด้วย `partial_fit` ที่รันคู่กับโมเดลต้นไม้ ถ้าต้องการใช้ neural network กับ NIDS จริง ๆ ควรใช้ sequence model บนลำดับ packet แทน MLP บนสถิติ flow ที่สรุปรวมแล้ว

### 3.7 Stacking Ensemble

**เอกสารทางการ:** https://scikit-learn.org/stable/modules/ensemble.html#stacked-generalization
**งานวิจัยต้นฉบับ:** **Wolpert, D. H. (1992) "Stacked Generalization" *Neural Networks* 5(2):241–259** · Breiman (1996) Stacked Regressions · Ting & Witten (1999) *JAIR* 10:271–289 · van der Laan et al. (2007) Super Learner

**สถาปัตยกรรมตามที่ implement จริง** (`src/models/stacking.py`):

```
StandardScaler
   └─> StackingClassifier (cv=5, stack_method='predict_proba', passthrough=False)
         ├─ LightGBM      (300 ต้น, 63 leaf, lr 0.05, class_weight='balanced')
         ├─ XGBoost       (200 ต้น, depth 8, lr 0.10, hist, ถ่วงน้ำหนักรายคลาส)
         ├─ RandomForest  (200 ต้น, class_weight='balanced')
         └─ meta: LogisticRegression (lbfgs, C=1.0, class_weight='balanced')
```

**อัลกอริทึมพื้นฐาน** — การเรียนรู้สองชั้น · ชั้น 0: base learner 3 ตัวสร้าง `predict_proba` แบบ out-of-fold ผ่าน CV ภายใน 5 fold · ชั้น 1: logistic regression แบบ balanced เรียนรู้การผสมเชิงเส้นบน meta-feature 27 มิติ (3 โมเดล × 9 คลาส) · ทฤษฎี Super Learner รับประกันว่า stack จะไม่แย่กว่า base learner ที่ดีที่สุด *ในเชิง asymptotic* แต่ไม่รับประกันบนข้อมูลจำกัดหรือเมื่อ distribution ของชุดทดสอบเลื่อน

**จุดแข็ง**
- detection rate รวม 0.9661 สูงเป็นอันดับสาม และ Heartbleed/Infiltration recall 1.0 (บน n=4 และ 11)
- DoS F1 0.9499 สูงเป็นอันดับสอง
- meta-learner แบบ logistic ตีความได้ว่า *โมเดลฐานตัวไหนถูกไว้ใจในคลาสไหน*

**จุดอ่อน (วัดได้)**
- **macro-F1 0.6822 ต่ำกว่าโมเดลฐานทั้งสามตัวเมื่อวัดแยก** (LightGBM 0.8774, XGBoost 0.8773, RF 0.8404) · base learner ใน stack ใช้ค่าตั้งต้นที่เล็กกว่าตัวที่ปรับแล้ว (`best_params: {}` ไม่มีการปรับระดับ ensemble)
- **Brute Force F1 เพียง 0.1946 (precision 0.1078)** เพราะ meta-learner ทำนาย BENIGN เป็น Brute Force จำนวนมาก (FPR ของคลาส Brute Force 3.03%) · โมเดลฐานทุกตัวแยก Brute Force ได้เกือบสมบูรณ์ ปัญหาจึงอยู่ที่ชั้น meta ไม่ใช่ชั้นฐาน
- **FPR 4.07% (alert ผิด 25,317 รายการ)** มากกว่า CatBoost 63 เท่า
- **เทรนนานที่สุด (2,754.7 วินาทีบน GPU)** เพราะ base learner แต่ละตัวถูก fit 6 ครั้ง (5 fold + refit)
- p95 latency 137.95 ms และไฟล์ 109.3 MB เพราะต้องรันทั้งสามโมเดลฐานแล้วตามด้วย meta-model
- ดำเนินงานยากที่สุด มี 4 โมเดลที่ต้องจัดเวอร์ชันและเฝ้าระวัง

**ความซับซ้อนเชิงคำนวณ** — เทรน `O((cv + 1) · Σᵢ Trainᵢ) + O(meta)` ≈ 6 เท่าของผลรวม base learner · ทำนาย `O(Σᵢ Inferᵢ + K·M)` คือผลรวมของ RF, XGB และ LGBM

**การตีความ** — ปานกลาง ชั้น meta ตีความได้ แต่การสาวกลับไปยังฟีเจอร์ต้องประกอบ SHAP ข้ามสองชั้น

**การใช้งานใน SOC** — **ไม่แนะนำในรูปแบบปัจจุบัน** · ถ้าจะใช้ ควรแก้ชั้น meta ก่อน เช่น ใช้ base learner ที่ปรับแล้ว เปิด `passthrough` หรือปรับ threshold ของ Brute Force แล้วประเมินใหม่ (หัวข้อ 5.2)

### 5.2 🟡 สิ่งที่ยังต้องทำ

1. **Bot ภายใต้การแบ่งตามเวลา** — ทุกโมเดลมี recall ราว 0.16 ต้องเพิ่มข้อมูล Bot จากช่วงเวลาหรือแหล่งอื่น หรือฟีเจอร์ที่จับพฤติกรรม C2 ได้คงที่กว่า ก่อนจะอ้างว่าระบบตรวจ Bot ได้
2. **รัน label-shuffle กับ run นี้** — run นี้ข้ามการตรวจนี้ไป (`skipped`) ควรรันเพื่อยืนยันว่าไม่มี leakage ผ่าน pipeline บนการแบ่งแบบใหม่
3. **จำกัด search space ของ LightGBM** — ค่าที่เลือกได้ยังเป็น `min_child_samples=1` ถ้ากลับไปใช้ oversample จะเสี่ยงท่องจำแถวที่ซ้ำเหมือน run เก่า ควรตั้งพื้นของ `min_child_samples` ไว้ในหลักร้อย และคุม `num_leaves < 2^max_depth`
4. **แก้ชั้น meta ของ Stacking** — ใช้ base learner ที่ปรับแล้ว พิจารณา `passthrough=True` และตรวจ false positive ของ Brute Force ก่อนประเมินใหม่
5. **ทดสอบความทนทานต่อการหลบเลี่ยง (evasion) ทั้ง 7 โมเดล** — ผู้โจมตีควบคุมฟีเจอร์ระดับ flow ได้ง่าย เช่น padding, การหน่วงเวลา และการแยก flow
6. **compile CatBoost/XGBoost ด้วย ONNX หรือ Treelite** และตรวจว่าผลทำนายตรงกับเดิม ก่อนนำไปใช้บนเส้นทาง inline

### 5.3 ผลการส่งผ่านข้ามชุดข้อมูล (CSE-CIC-IDS2018)

การทดลองเสริมในเล่มรายงานฝึกโมเดลทั้ง 7 ตัวใหม่บนโครงร่างคลาสร่วม 7 คลาส แล้วทดสอบข้ามระหว่าง CICIDS2017 และ CSE-CIC-IDS2018 พบว่าการส่งผ่านทำได้จำกัด macro-F1 สูงสุดอยู่ที่ 0.34 (2017→2018) และ 0.44 (2018→2017) เทียบกับ 0.86–0.88 ภายในชุดข้อมูลเดียวกัน และตัวจำแนกแยกได้ว่าระเบียนมาจากชุดข้อมูลใดด้วย AUC ≥ 0.999 · **ตัวเลขในเอกสารนี้จึงบอกประสิทธิภาพภายใน CICIDS2017 เท่านั้น** ไม่ได้รับประกันการใช้งานบนเครือข่ายอื่น รายละเอียดอยู่ใน `docs/experiments/crossdataset/round6_split_70_30/report/paper_summary_pack.md`

## 6. ข้อเสนอแนะสุดท้ายสำหรับการใช้งานใน SOC

### 6.1 การตัดสินใจ: CatBoost

| เกณฑ์ | CatBoost | หลักฐาน |
|---|---|---|
| **คุณภาพการทำนาย** | **อันดับ 1** | macro-F1 0.8873, balanced accuracy 0.8970, MCC 0.9844 สูงสุด · บน reportable macro-F1 ตามหลัง LightGBM 0.0014 จึงถือว่าเสมอกลุ่มบน |
| **การโจมตีที่พลาด** | **อันดับ 1** | 2,049 flow (FNR 1.60%) น้อยกว่า XGBoost 2.7 เท่า และ LightGBM 3 เท่า |
| **Latency / ขนาด** | **อันดับ 1 ในกลุ่มต้นไม้** | p95 8.39 ms ต่อ 1,000 flow, 2.5 MB · มีเพียง LogReg ที่เร็วกว่า แต่ FPR 16.9% |
| **ภาระ false positive** | อันดับ 3 | FPR 0.065% หรือ alert ผิด 6,500 รายการต่อ 10 ล้าน flow/วัน เทียบกับ 2,200 ของ LightGBM และ 3,800 ของ XGBoost |

**คำอธิบาย trade-off อย่างตรงไปตรงมา** — การเลือก CatBoost หมายถึงยอมรับ alert ผิดมากกว่า LightGBM ราว 4,300 รายการต่อ 10 ล้าน flow ปกติ เพื่อแลกกับการพลาดการโจมตีน้อยลงราว 4,200 flow บนชุดทดสอบนี้ และ latency ต่ำกว่า 17 เท่า ในงานความปลอดภัย การโจมตีที่หลุดหนึ่งครั้งมีต้นทุนสูงกว่า alert ผิดหนึ่งรายการ และ alert ผิดยังลดลงได้ด้วยการรวมกลุ่ม (ขั้นที่ 3 ด้านล่าง) ขณะที่การโจมตีที่หลุดไปแล้วกู้คืนไม่ได้

## 7. ข้อจำกัดของการประเมินนี้

1. **ใช้การแบ่งข้อมูลชุดเดียวและ random seed เดียว (42)** CV 5 fold ช่วยบอกความแปรปรวนบนชุดฝึก แต่ไม่ได้บอกความแปรปรวนของการแบ่งตามเวลา
2. **Heartbleed (n=4) และ Infiltration (n=11) ใช้สรุปไม่ได้** รายงานไว้เพื่อความครบถ้วน และมี `f1_macro_reportable` ที่ตัดสองคลาสนี้ออก
3. **การแบ่งตามเวลาใช้ลำดับแถวในไฟล์ ไม่ใช่ Timestamp** เพราะรุ่น MachineLearningCVE ไม่มีคอลัมน์เวลา และลำดับนี้คือลำดับที่ flow *จบ* ไม่ใช่ลำดับที่ *เริ่ม* การโจมตีที่ยาวนาน เช่น DoS GoldenEye จึงเลยช่วงเวลาการโจมตีไปได้
4. **CICIDS2017 มีข้อบกพร่องของ label ที่ถูกบันทึกไว้แล้ว** Engelen, Rimmer & Joosen (2021) พบข้อผิดพลาดทั้งในการติด label และการสกัดฟีเจอร์ และ Rosay et al. (2022) ยืนยันหลายข้อ ตัวเลขในรายงานนี้จึงควรอ่านเป็นขอบบน
5. **ผลภายในชุดข้อมูลเดียวไม่ได้รับประกันการใช้งานข้ามเครือข่าย** การทดลองข้ามชุดข้อมูลแสดงว่าประสิทธิภาพลดลงมาก (หัวข้อ 5.3)
6. **เวลาเทรนเทียบข้ามโมเดลไม่ได้** เพราะบางโมเดลเทรนบน GPU และบางโมเดลบน CPU
