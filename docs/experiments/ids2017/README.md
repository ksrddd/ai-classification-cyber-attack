# CICIDS2017 — สรุปการเทรนทุกรอบ

การเทรนฝั่ง 2017 ทำโดยเพื่อนร่วมทีม ไฟล์ที่ส่งมอบมาพร้อมข้อมูล สคริปต์ และการยืนยัน seed
อยู่ใน `cicids2017_handoff.zip`

---

### การ clean ที่ใช้

ทำทีละไฟล์แล้วค่อยรวม ตามลำดับนี้

1. ตัดช่องว่างหน้าชื่อคอลัมน์
2. บันทึก `_row_index` ก่อนทิ้งแถวใด ๆ เพื่อให้อ้างตำแหน่งแถวเดิมใน CSV ได้เสมอ
3. ปรับชื่อคอลัมน์อัตราให้ตรงกัน
4. ตัดคอลัมน์ซ้ำ `Fwd Header Length.1`
5. ตัดคอลัมน์ระบุตัวตน `Flow ID`, `Source IP`, `Destination IP`, `Source Port`, `Timestamp`
6. ตัด `Protocol` เพื่อไม่ให้กลายเป็นตัวบ่งบอกแหล่งที่มาของข้อมูล
7. ตัดแถว header ที่ปนมาเป็นข้อมูล
8. ยุบ sub-label เป็น 9 คลาสหลัก
9. แปลงเป็นตัวเลข, `inf` เป็น `NaN`, ทิ้งแถวที่มีค่าไม่สมบูรณ์
10. เก็บ feature เป็น `float32`
11. ตัดแถวซ้ำโดยเทียบ feature กับ label ไม่นับ metadata

**เก็บ `Destination Port` ไว้** เพราะมีความหมายเชิงบริการ ต่างจาก source port

### วิธีแบ่งข้อมูล

แบ่งตามลำดับเวลา 70/30 ภายในทุกกลุ่ม (ไฟล์ที่จับข้อมูล, คลาส) — 70% แรกของแต่ละคลาสใช้เทรน
30% ท้ายใช้ทดสอบ

**ทำไมไม่กันทั้งไฟล์ออก** เพราะใน CICIDS2017 แต่ละคลาสการโจมตีอยู่ในไฟล์เดียวเท่านั้น

| ไฟล์ | คลาสที่มี |
|---|---|
| Monday | BENIGN อย่างเดียว |
| Tuesday | Brute Force |
| Wednesday | DoS, Heartbleed |
| Thursday เช้า | Web Attack |
| Thursday บ่าย | Infiltration |
| Friday เช้า | Bot |
| Friday บ่าย DDos | DDoS |
| Friday บ่าย PortScan | PortScan |

กันไฟล์ใดออกก็เท่ากับคลาสนั้นไม่มีข้อมูลเทรนเลย

**ตัวบอกลำดับเวลา** ไฟล์รุ่น MachineLearningCVE ไม่มีคอลัมน์ `Timestamp` จึงใช้ลำดับแถวในไฟล์
(`_row_index`) แทน และตรวจกับตารางเวลาการโจมตีที่ CIC ประกาศไว้ ก่อนเทรนทุกครั้งไปป์ไลน์ตรวจ **1 คู่**
(DoS ก่อน Heartbleed) การตรวจ 7 คู่ที่มีในโค้ดไม่ได้ถูกเรียกใช้ รันด้วยมือแล้วผ่านทั้ง 7 คู่ แต่เมื่อตรวจว่า
"มีแถวใดสลับหรือไม่" พบแถว DoS GoldenEye 4,939 จาก 10,293 แถวอยู่หลัง Heartbleed ทั้งที่ตารางเวลาให้มาก่อน
ดูรายงาน `report/chronological_split_explained.md` ซึ่งอธิบายว่าลำดับนี้เรียงตามอะไร สะท้อนเวลาจริงได้แค่ไหน
และ test set ของแต่ละคลาสประกอบด้วย sub-attack ใดบ้าง

**ข้อควรระบุในรายงาน** CICFlowMeter สร้าง record ตอน flow จบ ไม่ใช่ตอนเริ่ม ลำดับจึงเป็นลำดับ
การจบ ซึ่งยังเป็นลำดับที่ถูกต้องสำหรับงาน IDS เพราะ feature vector ของ flow เกิดขึ้นได้ก็ต่อ
เมื่อ flow จบแล้ว

### การทูนที่แฟร์

ทุกโมเดลใช้วิธีเดียวกัน เป้าหมายเดียวกัน งบเท่ากัน (n_iter=20 บน 200,000 แถว) และ search space
เท่ากันที่ 144 ชุด ทุกตัวจึงได้ค้น 13.9% เท่ากัน

ไม่ทูน `max_iter` และ `class_weight` โดยตั้งใจ ตัวแรกจะทำให้เทียบโมเดลที่ยังไม่ converge กับ
ที่ converge แล้ว ตัวหลังจะทำให้โมเดลหนึ่งเลี่ยงการจัดการ imbalance ที่ตกลงกันไว้ได้

### คลาสที่มีปัญหา

**Bot ติดเพดานเดียวกันทุกโมเดล** — recall อยู่ระหว่าง 0.150 ถึง 0.161 ทั้งเจ็ดโมเดล

| โมเดล | Bot recall | Bot F1 |
|---|---|---|
| catboost | 0.1607 | 0.2061 |
| lightgbm | 0.1538 | 0.2514 |
| xgboost | 0.1607 | 0.2413 |
| random_forest | 0.1504 | 0.0459 |
| mlp | 0.1607 | 0.0096 |
| logistic_regression | 0.1573 | 0.0023 |

เมื่อโมเดลเชิงเส้นกับ gradient boosting ที่ทูนแล้วได้ recall เท่ากัน เพดานนั้นอยู่ที่ข้อมูล
ไม่ใช่ที่โมเดล เป็นอาการเดียวกับที่ฝั่ง 2018 เจอในคลาส SlowHTTPTest

**สองคลาสที่ test flow น้อยเกินไป** Heartbleed มี 4 แถว และ Infiltration มี 11 แถว รายงานจึง
ระบุ macro-F1 สองแบบ คือครบ 9 คลาส และเฉพาะ 7 คลาสที่มี test flow อย่างน้อย 30 แถว
