# SHAP บน protocol แบบแบ่ง 70/30: ผลที่เพิ่มและสิ่งที่เปลี่ยน

เอกสารนี้มีเฉพาะผลของ SHAP ที่รันใหม่บน split train 70% / test 30% และส่วนที่ต่างจากผลเดิมที่ train 60% วิธีทำ เกณฑ์ที่ตั้งไว้ก่อนรัน และเหตุผลการออกแบบเหมือนเดิมทุกอย่าง (ดู `shap_progress.md`) สคริปต์ ชุด feature F (13 ตัว) จำนวน seed (5) และจำนวนการสุ่ม null (2,000 ชุด) ไม่เปลี่ยน สิ่งเดียวที่เปลี่ยนคือสัดส่วนการแบ่งข้อมูล

ผลทุกส่วนใช้ split ของโปรโตคอล cross-dataset ยกเว้น Part A ของรอบ 1 ที่ใช้การแบ่งสุ่ม 70/30 ภายในของตัวเอง จึงเหมือนเดิม

ข้อสรุปหลักไม่เปลี่ยน คือไม่มีหลักฐานว่ากลุ่ม feature ที่บอก dataset (F) เป็นสาเหตุให้การโจมตีถูกทายเป็น Benign หลังย้าย dataset สิ่งที่เปลี่ยนมี 2 อย่าง อย่างแรกคือจำนวนคลาสที่ตัดสินได้เพิ่มขึ้น (Brute Force เข้ามา) เพราะที่ train 70% SSH-Patator ของ 2017 มี 474 แถวใน train (ที่ 60% มี 0 แถว) โมเดลที่เทรนจาก 2017 จึงทาย Brute Force ใน 2018 ถูกบางส่วนและมีแถว caught ให้เทียบ อย่างที่สองคือรอบ 3 กลุ่ม SHAP 26 ตัวมี 2 คลาสที่ผ่านเกณฑ์รายคลาสซึ่งฉบับ 60% ไม่มี (ดูหัวข้อ 4)

- กรณีที่ไม่ผ่านเกณฑ์จำนวนแถวแต่ได้ p < 0.05 (ไม่นับ): xgboost Brute Force 2018 -> 2017 (G_within = +0.191, p = 0.003, missed น้อยสุด 32 แถว)

## 7. ข้อจำกัดและสิ่งที่ยังไม่ทราบ

- ตัดสินได้เฉพาะ F กลุ่มเดียวและเฉพาะโมเดลต้นไม้ ยังไม่ได้ทดสอบว่าความสัมพันธ์ระหว่าง feature กับ decision boundary เปลี่ยนไปโดยตรง
- Part A ของ XGBoost ขยับโดยไม่ทราบสาเหตุ (หัวข้อ 4.3)
- กรณีรายคลาสที่ผ่านในรอบ 3 (XGBoost DoS, CatBoost DDoS) ยังไม่มีคำอธิบายกลไก XGBoost DoS ตรวจใน within-target แล้วไม่ผ่าน CatBoost DDoS ตรวจไม่ได้
- ผลรอบ 3 และ within-target ถูกรวมจากการรันขนานแยกโมเดลด้วยโหมด `--cached` ของสคริปต์เดิม (คำนวณตารางทั้งหมดใหม่จากค่า SHAP ที่บันทึกไว้) ล็อกของแต่ละเลนอยู่ในโฟลเดอร์ผลเป็น `run_<model>.log`
