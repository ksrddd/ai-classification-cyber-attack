# SHAP รอบ 4 (shift รายคลาส) บน protocol แบบแบ่ง 70/30

เอกสารนี้สรุปผลรอบ 4 ที่รันใหม่บน split train 70% / test 30% และส่วนที่ต่างจากผลเดิมที่ train 60% วิธีทำและเกณฑ์ตามที่ตั้งไว้ก่อนรันใน `results/crossdataset/importance_comparison/SHAP_ROUND4_PREREGISTRATION.md` ไม่เปลี่ยน (sha256 ของไฟล์ตรงกับที่บันทึกใน `summary.json`) สคริปต์ `scripts/shap_round4.py` ผลอยู่ใน `results/crossdataset/importance_comparison/shap_round4/`

รอบ 4 ไม่ fit โมเดลใหม่และไม่คำนวณ SHAP ใหม่ ใช้ค่า SHAP ของรอบ 2 (LightGBM) และรอบ 3 (RF, XGBoost, CatBoost) ที่รันใหม่บน 70/30 แล้ว ส่วนที่คำนวณใหม่คือ shift รายคลาส ซึ่งใช้แถวใน train ของ split แบบเรียงเวลา จึงเปลี่ยนตาม split ด้วย

## 1. คำถามของรอบ 4

รอบ 1-3 ไม่พบหลักฐานว่ากลุ่ม feature ที่บอก dataset (F) เป็นตัวดันการโจมตีที่ถูกทายพลาดไปทาง Benign แต่ F มาจาก adversarial validation ทั้ง dataset จึงบอกว่า feature ไหนแยก 2017 กับ 2018 ได้ ไม่ได้บอกว่า feature ไหนเปลี่ยนไป *สำหรับการโจมตีคลาสเดียวกัน* รอบ 4 ทดสอบตรงนี้ คือแรงดันไป Benign ในแถวที่ทายพลาดกระจุกอยู่ที่ feature ที่คลาสนั้นเลื่อนมากที่สุดระหว่าง 2 dataset หรือไม่

- S_c = 13 feature ที่ shift (Wasserstein-1 บนสเกลอันดับ) มากที่สุดของคลาส c
- G = ค่าเฉลี่ย 5 seeds ของ s(missed) - s(caught) โดย s คือสัดส่วนของ SHAP ไปทาง Benign ที่มาจาก S_c
- null = กลุ่มสุ่ม 13 feature 2,000 ชุด ผ่านเมื่อ G > 0 และ p < 0.05 / จำนวนคลาสที่นับได้ของโมเดลนั้น

## 2. สรุป

| ระดับ | train 60% (เดิม) | train 70% (ใหม่) |
|---|---|---|
| LightGBM | partial | partial |
| Random Forest | partial | สนับสนุน |
| XGBoost | ไม่สนับสนุน | ไม่สนับสนุน |
| CatBoost | สนับสนุน | สนับสนุน |
| รวม 4 โมเดล | partial | partial |

คำตัดสินรวมยังเป็น partial เหมือนเดิม (ต้องมีอย่างน้อย 3 ใน 4 โมเดลสนับสนุนจึงจะเป็นสนับสนุน) สิ่งที่เปลี่ยนคือ RF ขยับจาก partial เป็นสนับสนุน เพราะ Brute Force เข้ามาเป็นคลาสที่นับได้และผ่าน (เหตุเดียวกับรอบ 1-3 คือที่ train 70% SSH-Patator ของ 2017 มี 474 แถวใน train จึงมีแถว caught ให้เทียบ)

## 3. รายคลาส ทิศ 2017 -> 2018 (S_c 13 ตัว)

G (p) ใหม่ ในวงเล็บท้ายคือคำตัดสินรายคลาส

| โมเดล (เกณฑ์ p) | DDoS | DoS | Brute Force | Bot | Web Attack |
|---|---|---|---|---|---|
| lightgbm (0.0125) | +0.134 (0.100) ไม่สนับสนุน | +0.304 (0.005) สนับสนุน | -0.320 (0.999) ไม่สนับสนุน | นับไม่ได้ | +0.348 (0.001) สนับสนุน |
| random_forest (0.01) | +0.227 (0.038) กลาง ๆ | +0.371 (0.0005) สนับสนุน | +0.433 (0.0035) สนับสนุน | +0.446 (0.001) สนับสนุน | +0.233 (0.073) ไม่สนับสนุน |
| xgboost (0.0167) | +0.095 (0.188) ไม่สนับสนุน | +0.185 (0.0215) กลาง ๆ | นับไม่ได้ | นับไม่ได้ | +0.047 (0.408) ไม่สนับสนุน |
| catboost (0.01) | +0.293 (0.0005) สนับสนุน | +0.345 (0.0025) สนับสนุน | -0.328 (0.987) ไม่สนับสนุน | +0.106 (0.068) ไม่สนับสนุน | +0.281 (0.0065) สนับสนุน |

G (p) เดิม (train 60%)

| โมเดล | DDoS | DoS | Brute Force | Bot | Web Attack |
|---|---|---|---|---|---|
| lightgbm | +0.097 (0.189) ไม่สนับสนุน | +0.225 (0.036) กลาง ๆ | นับไม่ได้ | นับไม่ได้ | +0.351 (0.004) สนับสนุน |
| random_forest | +0.261 (0.017) กลาง ๆ | +0.358 (0.0005) สนับสนุน | นับไม่ได้ | +0.417 (0.001) สนับสนุน | +0.219 (0.084) ไม่สนับสนุน |
| xgboost | +0.060 (0.258) ไม่สนับสนุน | +0.167 (0.044) กลาง ๆ | นับไม่ได้ | นับไม่ได้ | +0.143 (0.124) ไม่สนับสนุน |
| catboost | +0.170 (0.033) กลาง ๆ | +0.335 (0.0015) สนับสนุน | นับไม่ได้ | นับไม่ได้ | +0.274 (0.013) สนับสนุน |

สิ่งที่เปลี่ยนจากฉบับ 60%

- DoS ใน LightGBM ขยับจากกลาง ๆ เป็นสนับสนุน (p 0.036 -> 0.005) ตอนนี้ DoS ผ่านใน 3 จาก 4 โมเดล และ XGBoost เกือบผ่าน (p = 0.0215 เกณฑ์ 0.0167) ตรงกับที่คาดไว้ใน pre-registration ว่า DoS น่าจะผ่านมากที่สุด
- DDoS ใน CatBoost ขยับจากกลาง ๆ เป็นสนับสนุน (p 0.033 -> 0.0005)
- Brute Force นับได้ใน 3 โมเดล ผลแยกทาง RF สนับสนุน (G = +0.433) แต่ LightGBM และ CatBoost ได้ G ติดลบชัด (-0.32 และ -0.33) คือในสองโมเดลนี้แถวที่ทายพลาดถูกดันไป Benign ผ่าน feature ที่ไม่ใช่ feature ที่ Brute Force เลื่อนมากที่สุด
- Bot ใน CatBoost เข้ามาเป็นคลาสที่นับได้ (ไม่สนับสนุน p = 0.068)
- XGBoost ยังไม่สนับสนุน และ Web Attack ใน RF ยังไม่สนับสนุนเหมือนเดิม

## 4. ส่วนที่รายงานแต่ไม่ใช้ตัดสิน

### 4.1 ทิศ 2018 -> 2017

S_c 13 ตัว ค่า p ต่ำกว่า 0.01 ได้แก่ DDoS ใน RF, XGBoost, CatBoost (p = 0.0005 ทั้งสาม) และ DoS ใน LightGBM (p = 0.002) DoS ใน RF และ CatBoost ไม่ผ่าน (p 0.44 และ 0.37) จึงไม่ได้สอดคล้องกับทิศหลักทุกคลาส

### 4.2 ขนาด S_c 5 และ 26 ตัว

ที่ 26 ตัว ทิศ 2017 -> 2018 RF ได้ p ต่ำกว่า 0.01 ในทั้ง 5 คลาสที่นับได้ LightGBM ได้ DDoS และ DoS (0.004, 0.0025) CatBoost ได้ DDoS และ DoS (0.0005, 0.0015) แนวโน้มคือยิ่งกลุ่มใหญ่ G ยิ่งห่างจาก null ซึ่งเข้ากับภาพว่า shift กระจายอยู่บนหลาย feature ไม่ได้อยู่แค่ 13 ตัวแรก

### 4.3 ความสัมพันธ์ระหว่าง shift กับส่วนต่าง SHAP

Spearman ระหว่าง shift(f, c) กับ d(f, c) บน 60 feature เป็นบวกเกือบทุกคลาส ทิศ 2017 -> 2018: RF 0.29-0.65, CatBoost 0.05-0.57, LightGBM 0.06-0.42, XGBoost -0.15-0.36 (ค่าลบตัวเดียวคือ Brute Force ของ XGBoost ซึ่งเป็นคลาสที่นับไม่ได้ในโมเดลนั้น)

### 4.4 S_c ซ้ำกับ F และกับ S_c ฉบับ 60% แค่ไหน

- S_c ซ้ำกับกลุ่ม consensus F ไม่มาก: DDoS 5, Brute Force 4, DoS 3, Bot 3, Web Attack 3, Infiltration 1 จาก 13 ตัว รอบ 4 จึงไม่ได้ทดสอบซ้ำรอบ 2
- S_c ฉบับ 70% ซ้ำกับฉบับ 60% เกือบทั้งหมด: DoS, Bot, Infiltration 13/13, DDoS และ Web Attack 12/13, Brute Force 10/13 ผลที่เปลี่ยนจึงมาจากค่า SHAP และแถว missed/caught ที่เปลี่ยน มากกว่าจากการเลือก feature

## 5. ความหมายเมื่ออ่านรวมกับรอบ 1-3

- รอบ 1-3: กลุ่ม feature ที่บอก dataset (F) ไม่ได้อธิบายว่าทำไมการโจมตีถูกทายเป็น Benign (ผลเดิมบน 70/30 ดู `shap_protocol_70_30.md`)
- รอบ 4: feature ที่การโจมตีคลาสนั้นเลื่อนมากที่สุดอธิบายได้บางส่วน ชัดที่สุดคือ DoS (ผ่าน 3 จาก 4 โมเดล) รองลงมาคือ Web Attack (ผ่าน 2) และ DDoS (ผ่าน 1, กลาง ๆ 1)
- อ่านรวมกัน: การทายพลาดหลังย้าย dataset น่าจะมาจาก shift ระดับคลาส มากกว่าจาก "ลายนิ้วมือ" ของ dataset แต่คำตัดสินรวมเป็น partial ตามเกณฑ์ จึงพูดได้ระดับรายคลาสและรายโมเดลเท่านั้น ไม่ได้อ้างเป็นข้อสรุปรวม

## 6. หมายเหตุการรันซ้ำ

- ค่า SHAP ของ RF และ CatBoost (รอบ 3) ที่รันบนเครื่องนี้ให้จำนวนแถว missed ตรงกับ log ของรอบ 3 ทุก seed
- XGBoost ให้จำนวนแถว missed ต่างกันได้ถึงประมาณ 1,200 แถวระหว่างเครื่อง น่าจะมาจาก `tree_method="hist"` กับ `n_jobs=-1` ที่จำนวน thread ต่างกัน ผล XGBoost ของรอบ 4 จึงอาจขยับเล็กน้อยถ้ารันบนเครื่องอื่น
- รันซ้ำได้ด้วย `python scripts/shap_round4.py --cached-shift` (ใช้ `blocks*.joblib` ของรอบ 2 และ 3 ที่รันบน 70/30 แล้ว)
