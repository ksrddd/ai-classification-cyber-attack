## สรุปสั้น

1. SHAP ให้ตารางบทบาทของ feature ต่างจาก permutation พอสมควร (kappa 0.37 และ 0.33 ต่ำกว่าเกณฑ์ 0.40) SHAP พบ feature ที่บอก dataset ได้ 26 ตัว ส่วน permutation พบ 18 ตัว
2. feature ที่เปลี่ยนกลุ่มประมาณครึ่งหนึ่งมี feature อื่นที่สหสัมพันธ์สูง (|r| >= 0.9) ซึ่งตรงกับจุดอ่อนของ permutation ที่คาดไว้
3. รอบ 1: คำถามว่า "การทายพลาดหลังย้าย dataset เกิดจาก fingerprint หรือไม่" ขึ้นกับว่าใช้ตารางไหน (ตาราง SHAP ได้ partial ตาราง permutation ได้ไม่สนับสนุน)
4. รอบ 2 (เพิ่ม null จากการสุ่มกลุ่ม feature): **ไม่สนับสนุน ทุกกลุ่ม feature** ส่วนต่างที่เห็นในรอบ 1 เช่น DDoS +0.139 อยู่ในช่วงที่กลุ่ม feature แบบสุ่มขนาดเท่ากันก็ให้ได้ (p = 0.14) จึงยังไม่มีหลักฐานว่า feature ที่บอก dataset เป็นตัวผลักให้ทายพลาดเป็น Benign
5. ตรวจความทนทาน: การเปลี่ยนโหมด SHAP แทบไม่มีผล (Spearman 0.98) ส่วนความต่างของ Part A มาจากเกณฑ์ตัดสินส่วนหนึ่ง (ใช้ top-K เดียวกัน kappa ขึ้นเป็น 0.40 ถึง 0.62)
6. รอบ 3 (RF, XGBoost, CatBoost ด้วยวิธีของรอบ 2): **ไม่สนับสนุน ทั้ง 3 โมเดล ทุกกลุ่ม feature** ผลของรอบ 2 จึงไม่ได้เกิดกับ LightGBM ตัวเดียว

## 2. ทำไมต้องทำ SHAP

งานก่อนหน้า (`dataset_vs_attack_importance.py`) แบ่ง feature 60 ตัวเป็น 4 กลุ่ม
คือ fingerprint only, attack only, entangled และ neither โดยใช้ permutation importance

permutation importance มีจุดอ่อนเรื่อง feature ที่ซ้ำกัน ถ้าสอง column มีข้อมูลเดียวกัน
สลับค่า column หนึ่งแล้วโมเดลก็ยังอ่านอีก column ได้ ทำให้ทั้งสองตัวได้คะแนนใกล้ 0
ผล adversarial validation บอกแล้วว่าสัญญาณที่บอก dataset กระจายอยู่หลาย column
จึงเป็นไปได้ว่าตารางบทบาทของ feature ได้รับผลจากจุดอ่อนนี้

SHAP แบ่งคะแนนให้ column ที่ซ้ำกันแทนที่จะให้ 0 ทั้งคู่ และอธิบายได้รายแถว
งานนี้จึงมี 2 ส่วน

- **Part A** ตรวจว่าตารางบทบาทของ feature ยังเหมือนเดิมไหมเมื่อใช้ SHAP
- **Part B** ดูการโจมตีที่โมเดลทายพลาดเป็น Benign หลังย้าย dataset ว่าถูกผลักด้วย feature กลุ่มไหน

## 3. เกณฑ์ที่ตั้งไว้ก่อนรัน

ไฟล์: `results/crossdataset/importance_comparison/SHAP_PREREGISTRATION.md`

**Part A**
- ใช้ข้อมูลและการแบ่งเหมือนงาน permutation ทุกอย่าง (60 features, seed 42-46, 70/30)
- โมเดล LightGBM และ Logistic Regression
- feature ที่ถือว่า "ใช้งาน" ต้องมีส่วนแบ่ง SHAP อย่างน้อย 1/60 และเป็นแบบนั้นใน 4 จาก 5 seeds
- เทียบกับตารางเดิมด้วย Cohen's kappa
  - kappa >= 0.60 ทั้งสองโมเดล = ยืนยันตารางเดิม
  - kappa < 0.40 โมเดลใดโมเดลหนึ่ง = ไม่ยืนยัน
  - นอกนั้น = partial

**Part B**
- LightGBM แบบเดียวกับ protocol (77 features, 7 classes, แบ่งตามเวลา) ทิศหลักคือ 2017 ไป 2018
- missed = การโจมตีใน test ของอีก dataset ที่ถูกทายเป็น Benign
- caught = การโจมตีคลาสเดียวกันใน test ของ dataset เดิมที่ทายถูก
- วัดว่าแรงที่ผลักไปทาง Benign มาจาก feature กลุ่ม fingerprint only หรือ entangled กี่ส่วน (ค่า s)
- ถ้า s(missed) - s(caught) >= 0.10 ทุก seed ในคลาสส่วนใหญ่ = fingerprint ทำให้ทายพลาด
- ถ้าต่างกันไม่เกิน 0.02 ในคลาสส่วนใหญ่ = ไม่สนับสนุน
- นอกนั้น = partial

## 4. สิ่งที่ทำไปแล้ว

1. ติดตั้ง `shap` 0.52.0 ใน `.venv` (มีใน `requirements.txt` แต่ยังไม่ได้ติดตั้ง)
2. เขียน `scripts/shap_importance.py` ใช้ฟังก์ชันเดิมจากสคริปต์ของเพื่อน (`dataset_vs_attack_importance.py`, `adversarial_validation.py`, `run_crossdataset.py`) เพื่อให้ข้อมูล การแบ่ง และโมเดลเหมือนกันทุกอย่าง
3. ทดสอบโค้ดกับข้อมูลชุดเล็ก (1 seed, 20,000 แถวต่อ dataset) ใช้ไฟล์ตัวอย่าง 2018 ที่ทำความสะอาดเองเฉพาะสำหรับทดสอบ ตัวเลขจากการทดสอบนี้ **ไม่ใช่ผลการทดลอง** ใช้ดูแค่ว่าโค้ดทำงานถูก

## 5. สิ่งที่เจอระหว่างทดสอบ และสิ่งที่แก้

ทุกข้อแก้ก่อนรันจริง และบันทึกไว้ในไฟล์เกณฑ์แล้ว

| เรื่องที่เจอ | ที่แก้ |
|---|---|
| SHAP แบบ interventional ของ LightGBM ใช้เวลา 9 นาทีต่อ 1 ครั้ง ถ้ารันครบจะใช้ประมาณ 20 ชั่วโมง | LightGBM เปลี่ยนเป็นแบบ tree_path_dependent ทดสอบทั้งหมดเหลือ 1.4 นาที |
| `shap` ลด background จาก 200 เหลือ 100 แถวเองโดยไม่บอก | กำหนด `max_samples` ให้ใช้ครบ 200 (Logistic Regression) |
| Part B เอาคลาส Infiltration มาตัดสินทั้งที่ฝั่ง caught มีแค่ 10 แถว | เพิ่มเกณฑ์ caught อย่างน้อย 30 แถว (ค่าเดียวกับ protocol) |
| เกณฑ์ฝั่ง attack ยังไม่ได้บอกว่านับ dataset ไหน | ใช้ "dataset ใดก็ได้" เหมือนงาน permutation |
| จำกัดแถวใน Part B ที่ 2,000 ต่อกลุ่ม ทำให้คลาสเล็กแทบไม่เหลือ | เปลี่ยนเป็น 1,000 แถวต่อคลาส |

เรื่องการเปลี่ยนเป็น tree_path_dependent: ตอนแรกตั้งใจใช้ interventional ทั้งสองโมเดล
เพื่อให้วัดแบบเดียวกัน แต่ kappa ของแต่ละโมเดลเทียบกับตาราง permutation ของโมเดลตัวเอง
การที่สองโมเดลใช้คนละแบบจึงไม่กระทบการตัดสินของ Part A

## 7. ผล Part A: ตารางบทบาทของ feature

**คำตัดสินตามเกณฑ์: ไม่ยืนยัน** (kappa ต่ำกว่า 0.40 ทั้งสองโมเดล)

| | LightGBM | Logistic Regression |
|---|---|---|
| Cohen's kappa | 0.366 | 0.334 |
| Spearman ของอันดับ attack importance (2017 / 2018) | 0.68 / 0.68 | 0.74 / 0.88 |
| feature ที่เปลี่ยนกลุ่ม | 25 จาก 60 | 29 จาก 60 |
| ในนั้นมีคู่ที่สหสัมพันธ์ >= 0.9 | 13 | 16 |
| ในนั้นเป็นตัวแทนกลุ่ม feature ซ้ำ | 7 | 6 |

จำนวน feature ในแต่ละกลุ่ม

| กลุ่ม | LightGBM (perm / SHAP) | LR (perm / SHAP) |
|---|---|---|
| fingerprint only | 10 / 13 | 2 / 12 |
| entangled | 8 / 13 | 16 / 14 |
| attack only | 9 / 5 | 33 / 18 |
| neither | 33 / 29 | 9 / 16 |

สิ่งที่เห็น
- ฝั่ง dataset SHAP พบ feature ที่บอก dataset ได้ 26 ตัว ส่วน permutation พบ 18 ตัว ตรงกัน 13 ตัว SHAP พบเพิ่ม 13 ตัว และไม่นับ 5 ตัวที่ permutation นับ
- LightGBM มี feature ที่ permutation ให้เป็น neither ย้ายไป fingerprint only 6 ตัว และ entangled 3 ตัว ตรงกับที่ทำนายไว้ในเกณฑ์ ส่วนกลุ่ม entangled เดิม 7 จาก 8 ตัวยังอยู่ที่เดิม
- LR ต่างมากเพราะเกณฑ์ 1/60 เข้มกว่าเกณฑ์ noise floor ของ permutation สำหรับ LR feature ที่นับว่ามีสัญญาณการโจมตีลดจาก 39 / 33 ตัว เหลือ 25 / 16 ตัว (2017 / 2018) LR กระจายน้ำหนักไปหลาย feature ส่วนแบ่งแต่ละตัวจึงต่ำกว่า 1/60 ได้ง่าย ความต่างของ LR จึงมาจากเกณฑ์ตัดสินส่วนหนึ่ง ไม่ได้มาจากวิธี SHAP อย่างเดียว
- feature ที่เปลี่ยนกลุ่มประมาณครึ่งหนึ่งมีคู่ที่สหสัมพันธ์สูง เช่น Packet Length Mean กับ Average Packet Size, Fwd IAT Max กับ Idle Max ตรงกับเหตุผลที่ทำ SHAP ตั้งแต่แรก
- หมายเหตุ: การตรวจสหสัมพันธ์ใช้ข้อมูล 2017 ครบ 60 features แต่ไฟล์ 2018 ตรงชื่อแค่ 24 ตัว (ชื่อ column ต่างกัน) ผลส่วนนี้จึงอิง 2017 เป็นหลัก

## 8. ผล Part B: การโจมตีที่ถูกทายพลาดหลังย้าย dataset

ทิศหลัก 2017 ไป 2018 ค่าเฉลี่ย 5 seeds (s = ส่วนของแรงที่ผลักไปทาง Benign
ที่มาจาก feature กลุ่ม fingerprint only และ entangled)

| คลาส | ถูกตัดสินไหม | s(missed) - s(caught) ตาราง SHAP | ตาราง permutation |
|---|---|---|---|
| DDoS | ใช่ | +0.139 (ทุก seed >= 0.10) | -0.076 |
| DoS | ใช่ | +0.135 (4 จาก 5 seeds >= 0.10) | +0.054 |
| Web Attack | ใช่ | -0.054 | -0.098 |
| Infiltration | ไม่ (caught แค่ 10 แถว) | +0.224 | 0.000 |
| Bot | ไม่ (missed แค่ 8 แถว) | +0.050 | -0.065 |
| Brute Force | ไม่ (caught 0 แถว) | - | - |

**คำตัดสินตามเกณฑ์**
- ใช้ตาราง SHAP: **partial** (สนับสนุน 1 คลาส, ไม่สนับสนุน 1 คลาส, กลาง ๆ 1 คลาส)
- ใช้ตาราง permutation: **ไม่สนับสนุน**
- เนื่องจาก Part A ไม่ยืนยัน ต้องรายงานทั้งสองแบบ ตามที่เขียนไว้ในเกณฑ์

สิ่งที่เห็น
- คำตอบของ Part B ขึ้นกับว่าใช้ตารางไหนนิยาม feature fingerprint ตอนนี้จึงยังพูดไม่ได้ว่า fingerprint เป็นสาเหตุที่ทำให้ทายพลาด
- กับ DDoS ผลชัดที่สุด ถ้าใช้ตาราง SHAP ทุก seed ได้ส่วนต่างเกิน 0.10 (0.113 ถึง 0.165)
- Web Attack ไปทางตรงข้ามในทั้งสองตาราง
- Brute Force ของ 2017 ในการแบ่งตามเวลาได้ F1 = 0 อยู่แล้วใน `protocol_v2` จึงไม่มีแถวที่ทายถูกให้เทียบ ไม่ใช่ปัญหาของสคริปต์นี้
- ค่า s ของตาราง SHAP สูงกว่า (0.6 ถึง 0.8) เพราะกลุ่ม F มี 26 ตัว ส่วนตาราง permutation มี 18 ตัว การเทียบจึงดูที่ส่วนต่างภายในตารางเดียวกันเท่านั้น

ทิศ 2018 ไป 2017 (รายงานไว้ แต่ไม่ใช้ตัดสิน) ส่วนต่างเป็นบวกเกือบทุกคลาส
เช่น DDoS +0.341 (ตาราง SHAP) และ +0.197 (ตาราง permutation), Web Attack +0.218 และ +0.178
ทิศนี้ย้าย dataset ได้ดีกว่าอยู่แล้ว ผลนี้น่าสนใจแต่ไม่ได้อยู่ในเกณฑ์ตัดสิน

## 9. ข้อจำกัด

- LightGBM ใช้ SHAP แบบ path-dependent ส่วน LR ใช้แบบ interventional (เหตุผลอยู่ในข้อ 5)
- เกณฑ์ 1/60 ไม่ได้เหมาะกับทุกโมเดลเท่ากัน โมเดลที่กระจายน้ำหนัก เช่น LR จะมี feature ผ่านเกณฑ์น้อยกว่า
- Part B ตัดสินได้แค่ 3 คลาส จาก 6 คลาสการโจมตี
- ใช้แค่ LightGBM และ LR ยังไม่ได้ทำ RF, XGBoost, CatBoost

## 10. ขั้นต่อไปที่เป็นไปได้

1. ให้เพื่อนตรวจผลและเกณฑ์ ก่อนนำไปเขียนในรายงานหลัก
2. ขยาย Part A และ B ไป RF, XGBoost, CatBoost ด้วยเกณฑ์เดิม (TreeExplainer เร็ว)
3. ดู DDoS เป็นกรณีศึกษา ว่า feature ไหนผลักไปทาง Benign มากที่สุด
4. นำผลไปใช้กับงาน binary และ distribution alignment ที่ยังค้างอยู่

## 11. ตรวจความทนทาน 1a: เปลี่ยนเกณฑ์ตัดสิน

เป็นการวิเคราะห์เพิ่มเติม ไม่ได้เปลี่ยนคำตัดสินของ Part A สคริปต์ `scripts/shap_threshold_check.py` ใช้ผลที่บันทึกไว้ ไม่ได้เทรนใหม่

Part A รอบ 1 เปลี่ยนสองอย่างพร้อมกัน คือวิธีวัด (SHAP แทน permutation) และเกณฑ์ (1/60 แทน noise floor) ข้อนี้ใช้เกณฑ์ top-K แบบเดียวกันกับทั้งสองวิธี เพื่อดูผลของวิธีวัดอย่างเดียว

| K | ฝั่ง dataset ตรงกัน | kappa LightGBM | kappa LR |
|---|---|---|---|
| 5 | 80% | 0.524 | 0.486 |
| 10 | 77% | 0.448 | 0.411 |
| 15 | 83% | 0.517 | 0.622 |
| 20 | 80% | 0.403 | 0.481 |

เมื่อใช้เกณฑ์เดียวกัน kappa ขึ้นจาก 0.33 ถึง 0.37 เป็น 0.40 ถึง 0.62 ความต่างในรอบ 1 จึงมาจากเกณฑ์ส่วนหนึ่ง แต่สองวิธีก็ยังไม่ตรงกันทั้งหมด (ส่วนใหญ่อยู่ในช่วง "moderate")

## 12. ตรวจความทนทาน 1b: เปลี่ยนโหมด SHAP

สคริปต์ `scripts/shap_mode_check.py` ใช้ LightGBM ของ Part A หนึ่งตัว (2017, seed 42) อธิบาย 300 แถวเดียวกันทั้งสองแบบ (background 100 แถว)

| | ค่า |
|---|---|
| Spearman ของส่วนแบ่ง feature | 0.98 |
| top-10 feature ตรงกัน | 10 จาก 10 |
| ผ่านเกณฑ์ 1/60 | 15 ตัวทั้งสองแบบ ตัดสินตรงกัน 96.7% |

## 14. สรุปรวมทั้งหมด

1. SHAP กับ permutation ไม่ตรงกันพอที่จะยืนยันตารางบทบาทของ feature (Part A) ส่วนหนึ่งเพราะเกณฑ์ ส่วนหนึ่งเพราะ feature ที่ซ้ำและสัมพันธ์กัน

3. ผลนี้ชี้ว่าการตัด feature fingerprint ทิ้งอย่างเดียวไม่น่าจะแก้ปัญหาการย้าย dataset ได้ ซึ่งสอดคล้องกับผล ablation เดิมที่ตัด feature แล้วไม่ดีขึ้น
