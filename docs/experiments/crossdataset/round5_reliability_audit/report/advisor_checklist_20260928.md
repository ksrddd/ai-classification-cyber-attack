## 1. ผลตรวจ AUC ครบทุกด้าน

### 1.1 สิ่งที่เปลี่ยนจากรอบก่อน

สคริปต์ตรวจเดิมรัน model ladder, near-duplicate และ null control **แค่ seed 42 ตัวเดียว** แล้ว
รายงานผลนั้นเหมือนเป็นคำตอบ และ **ยังไม่มี label-shuffle** เลย รอบนี้แก้ให้ทุกการตรวจที่ขึ้นกับ
การสุ่มรันครบทั้ง 5 seeds และเพิ่ม label-shuffle

label-shuffle กับ null control เป็นคนละการทดสอบกัน

- **null control** เอา dataset เดียวมาแบ่งครึ่งแบบสุ่ม แล้วดูว่าวิธีการสร้างการแยกขึ้นมาเองได้ไหม
- **label-shuffle** ใช้แถวจริงชุดเดียวกับผลหลักทุกแถว แต่สลับ label 2017/2018 ทิ้งก่อนแบ่งข้อมูล ถ้ายังได้ AUC สูง แปลว่า pipeline รู้ label ผ่านช่องทางอื่นที่ไม่ใช่ feature

### 1.2 AUC หลักทั้ง 5 seeds

LightGBM ตัวเดียวกับที่ใช้ทำ adversarial validation รันซ้ำแล้วได้ค่าเท่ากับรอบตรวจก่อนทุกตำแหน่ง
ขนาดตัวอย่างสูงสุด 8,000 แถวต่อฝั่ง

### 1.3 Duplicate และ near-duplicate

near-duplicate คือแถว test ที่อยู่ใกล้แถว train มากกว่าระยะที่แถว train อยู่ห่างกันเองถึง 99.9%
ของกรณี เกณฑ์นี้ตั้งมาจากข้อมูลเอง ระดับที่เกิดขึ้นได้โดยบังเอิญจึงเท่ากับ 0.10% พอดี

|---|---|---:|---:|

| DoS | 0 0 0 0 0 | 0.16% | 0.29% |
| Brute Force | 0 0 0 0 0 | 0.20% | 0.41% |
| Bot | 0 0 0 0 0 | 0.17% | 0.34% |
| **DDoS** | 0 0 0 0 0 | **6.82%** | 7.17% |
| **Web Attack** | 0 0 0 0 0 | **2.75%** | 4.07% |

**ไม่มีแถวซ้ำเป๊ะคร่อม train/test เลยสักแถวในการสุ่มทั้ง 30 ครั้ง** DDoS กับ Web Attack มี
near-duplicate สูงกว่าระดับบังเอิญจริงในทุก seed แต่ไม่ได้อธิบายค่า AUC เพราะ decision stump

## 2. Control ภายใน dataset เดียวกัน

### 2.1 ทำไมต้องทำ

null control ในข้อ 1 พิสูจน์ได้แค่ว่า *วิธีการ* ไม่สร้างการแยกขึ้นมาเอง แต่พิสูจน์ *ข้อสรุป*
ไม่ได้ เพราะการแบ่งแบบสุ่มคลุกทุกวันที่เก็บข้อมูลเข้าไปทั้งสองฝั่ง ความต่างที่ผูกกับช่วงเวลา
ที่เก็บข้อมูลจึงรอดไม่ได้ตั้งแต่ต้น

control นี้จึงลากเส้นแบ่ง *ภายใน* dataset เดียวแล้วรักษาโครงสร้างไว้ ถ้าคนละวันในคลังเดียวกัน
แยกได้ดีพอ ๆ กับ 2017 เทียบ 2018 สิ่งที่เรียกว่า dataset fingerprint ก็เป็นแค่ความต่างตาม
ปกติระหว่างการเก็บข้อมูลแต่ละครั้ง

### 2.2 วิธี

- ใช้ขั้นตอนเดียวกับ adversarial validation ทุกอย่าง และรันด้วยโมเดลของ protocol **ครบทั้ง 7 ตัว** กับ stump
- เส้นแบ่งภายใน dataset มีสองแบบ คือครึ่งแรกเทียบครึ่งหลังตามลำดับเวลา และ capture file ชุดหนึ่งเทียบอีกชุด
- **ทุกเส้นแบ่งในคลาสเดียวกันใช้จำนวนแถวต่อฝั่งเท่ากัน** เพราะ AUC ขยับตามขนาดตัวอย่าง
- แบ่ง capture file ด้วยขนาด ไม่ใช่เรียงตามวันที่ มิฉะนั้นจะได้การแบ่งตามเวลาซ้ำอีกรอบ
- เขียนกติกาการอ่านผลไว้ก่อนรัน

## 3. Dataset Importance เทียบกับ Attack Importance

### 3.1 วิธี

- **Dataset importance** คือ permutation importance จาก adversarial validation ที่รันไว้แล้ว ไม่ได้คำนวณใหม่
- **Attack importance** คือ permutation importance ของตัวจำแนก attack ภายในแต่ละ dataset วัดด้วย macro-F1 ใช้โมเดลของ protocol ตัวจริง และทำ preprocess, reseed และ fit เหมือนตอนทำ transfer ทุกอย่าง
- วัดกับสองโมเดล คือ **LightGBM** ซึ่งเสียหนักที่สุดตอน ablation และ **Logistic Regression** ซึ่ง ablation ไม่กระทบ และ transfer ทิศ 2018 ไป 2017 ได้ดีที่สุด
- ใช้ 60 features ชุดเดียวกัน 5 seeds

วัดสองแบบ เพราะแต่ละแบบมีจุดบอดคนละที่

- **permutation importance** บอกว่าโมเดลพึ่งคอลัมน์ไหนจริง แต่ถ้ามีหลายคอลัมน์ที่ให้ข้อมูลซ้ำกัน มันจะให้คะแนนต่ำทั้งหมด
- **univariate** ไม่ใช้โมเดลเลย ฝั่ง dataset ใช้ AUC ของคอลัมน์เดี่ยวระหว่างสอง dataset ฝั่ง attack ใช้ mutual information ระหว่างคอลัมน์กับคลาส attack

feature จะถือว่า "ใช้งาน" ในงานใดงานหนึ่งก็ต่อเมื่อ importance เฉลี่ยเป็นบวก และมากกว่าสองเท่า
ของส่วนเบี่ยงเบนระหว่าง seed เกณฑ์นี้ตั้งจากความแปรปรวนของการวัดเอง ไม่ได้เลือกด้วยตา

### 3.2 คำตอบหลัก

**คอลัมน์ที่บอก dataset กับคอลัมน์ที่ใช้จำแนก attack เป็นชุดเดียวกันเป็นส่วนใหญ่**

| rank correlation ระหว่างสองอย่าง (60 features) | 2017 | 2018 |
|---|---:|---:|
| **univariate** แยก dataset ได้ดีแค่ไหน เทียบกับ attack MI | **+0.72** | **+0.77** |
| permutation ของ LightGBM | +0.35 | +0.40 |
| permutation ของ Logistic Regression | -0.07 | +0.24 |

ค่าจาก univariate น่าเชื่อกว่าเพราะไม่มีปัญหาคอลัมน์ซ้ำ ฝั่ง dataset ของ permutation importance
มี 48 จาก 60 features ที่คะแนนเกือบศูนย์เพราะปัญหานี้

ตระกูลขนาด packet อยู่อันดับต้นของทั้งสองด้านพร้อมกัน

| feature | AUC คอลัมน์เดี่ยวข้าม dataset | attack MI 2017 | attack MI 2018 |
|---|---:|---:|---:|
| Packet Length Mean | 0.8290 | 0.4965 | 0.2633 |
| Average Packet Size | 0.8279 | 0.5282 | 0.2599 |
| Packet Length Std | 0.8105 | 0.4777 | 0.2736 |
| Max Packet Length | 0.8054 | 0.4796 | 0.2747 |

### 3.3 บทบาทของแต่ละ feature

มี 18 features ที่แยก dataset ได้เกินระดับ noise อย่างน้อยในหนึ่งคลาส

| บทบาท | ตรงกันทั้ง LightGBM และ Logistic Regression |
|---|---|
| **fingerprint อย่างเดียว** ตัดทิ้งได้โดยไม่เสีย attack signal | **มีตัวเดียว คือ `act_data_pkt_fwd`** |
| **ใช้ทั้งสองอย่าง** | `min_seg_size_forward`, `Init_Win_bytes_forward`, `Init_Win_bytes_backward`, `Destination Port`, `Flow IAT Min`, `Fwd Packet Length Std`, `Bwd Packet Length Std` |

อีก 10 ตัวขึ้นกับโมเดล เป็น fingerprint อย่างเดียวสำหรับ LightGBM แต่ Logistic Regression
เอาไปใช้จำแนก attack

### 3.4 ทำไม ablation ทำให้ tree model แย่ลงแต่ Logistic Regression ไม่เป็นไร

feature 10 อันดับแรกที่ ablation ตัดทิ้ง คิดเป็นสัดส่วนเท่าไหร่ของ attack importance

| โมเดล | 2017 | 2018 |
|---|---:|---:|
| LightGBM | **80.8%** | **78.9%** |
| Logistic Regression | 12.6% | 31.1% |

ตัวหลักคือ `Destination Port` ซึ่งด้าน dataset อยู่อันดับ 6 แต่เป็น feature ที่ LightGBM ใช้จำแนก
attack มากที่สุด ประมาณ 40% ของ importance ทั้งหมด

ข้อจำกัด ที่ K=5 สัดส่วนนี้ของ LightGBM เหลือเพียง 10% ถึง 27% แต่ transfer ของ LightGBM ตก
หนักตั้งแต่ K=5 แล้ว จาก 26.2% เหลือ 9.9% importance ภายใน dataset จึงอธิบายการตกได้ส่วนหนึ่ง
ไม่ใช่ทั้งหมด

### 3.5 ข้อค้นพบเพิ่ม: RST Flag Count

| | 2017 | 2018 |
|---|---:|---:|
| สัดส่วนที่เป็นศูนย์ | **99.97%** | 76.3% |

`ECE Flag Count` กระจายตัวแบบเดียวกันทุกอย่าง โมเดลที่เทรนบน 2017 จึงใช้คอลัมน์นี้ไม่ได้เลย
(importance เท่ากับศูนย์พอดี) เป็นไปได้ว่าตัวดึง feature ของสอง dataset นับ TCP flag ไม่เหมือนกัน
**ข้อนี้ยังไม่ได้ยืนยันกับเอกสารของ CIC**

### 3.6 สรุปข้อ 3

ไม่มีชุด fingerprint ที่แยกออกมาตัดทิ้งได้อย่างสะอาด ซึ่งอธิบายได้ว่าทำไม ablation ในรอบก่อน
ถึงไม่ช่วย และทำไมมันทำร้าย tree model มากกว่าโมเดลเชิงเส้น ทางที่เหลืออยู่จึงเป็น target
adaptation หรือการเทรนร่วมสอง dataset ซึ่งอาจารย์กันไว้ไม่ให้ทำในขั้นนี้

## 4. ผล Cross-Dataset หลังแก้ Clean-before-Sampling

### 4.1 สิ่งที่เปลี่ยน

protocol v1 สุ่มคลัง 2018 ให้เหลือ 300,000 แถว **ก่อน** ทำความสะอาด ส่วน protocol v2 สร้างคลัง
2018 ใหม่จากไฟล์ดิบ 10 ไฟล์ ทำความสะอาดก่อนแล้วค่อยสุ่ม เหมือนที่ฝั่ง 2017 ทำมาตลอด

ทั้งสองรอบใช้ 7 โมเดล 2 วิธีแบ่ง 5 seeds และ schema เดียวกัน **สิ่งเดียวที่เปลี่ยนคือลำดับการ
เตรียมข้อมูลของคลัง 2018** ความต่างทุกอย่างจึงมาจากการแก้นี้

### 4.2 Asymmetry ยังอยู่ แต่เล็กลง

ค่า recovered % แบ่งตามเวลา คือส่วนของระยะจาก baseline ถึง ceiling ที่ transfer ปิดได้

|---|---:|---:|

| 2018 ไป 2017 เฉลี่ย | 44.6% | 39.3% |

| asymmetry median | 48.0 จุด | 34.3 จุด |
| โมเดลที่ 2018 ไป 2017 ดีกว่า | 7 จาก 7 | **7 จาก 7** |
| โมเดลที่ดีที่สุดทิศ 2018 ไป 2017 | stacking 73.9% | **logistic_regression 79.8%** |

รายโมเดล แบ่งตามเวลา

ทิศทางเหมือนเดิมทุกโมเดล และทิศ 2017 ไป 2018 ยังเกือบเท่า baseline แต่ลำดับโมเดลในทิศ
2018 ไป 2017 เปลี่ยนไปมาก stacking ที่เคยดีที่สุดตกจาก 73.9% เหลือ 40.2%

ถ้ารันเฉพาะการแบ่งแบบสุ่มจะสรุปว่าสองทิศยากพอกัน ข้อนี้ **ไม่เปลี่ยนหลังการแก้**

สาเหตุคือการแบ่งแบบสุ่มดัน ceiling ของ 2017 ขึ้นมาก เมื่อ ceiling สูงขึ้น recovered % ของทุก

### 4.4 Ceiling และ inflation

| | v1 | v2 |
|---|---:|---:|

จึงเรียนรู้ได้ ส่วน inflation ของ 2018 ที่ลดลงครึ่งหนึ่งนั้น 70% ของค่าเดิมมาจาก Web Attack ซึ่งเคยมี test
เพียง 5 แถว ไม่ใช่เพราะปิด leakage การ dedup ทำก่อนการแบ่งข้อมูลทั้งสองรอบอยู่แล้ว

### 4.5 Control ในตัว

คลัง 2017 ไม่ได้ถูกแตะเลย ค่า ceiling จึงควรออกมาเท่าเดิม

สามโมเดลที่ผลคงที่ทุกครั้งให้ค่าเท่าเดิมพอดี ส่วนสี่โมเดลที่ขยับเป็นโมเดลที่ผลแต่ละรอบไม่
ตายตัวอยู่แล้ว **ยืนยันว่าความเปลี่ยนแปลงทั้งหมดมาจากฝั่ง 2018**

### 4.6 สรุปข้อ 4

การแก้ไม่ได้ล้มข้อสรุปหลัก asymmetry ยังอยู่ และการแบ่งแบบสุ่มยังซ่อนมันไว้เหมือนเดิม
แต่ขนาดของ asymmetry ลดลงราว 7 จุด และลำดับโมเดลใน transfer เปลี่ยนไปพอสมควร ตัวเลข
stacking 73.9% ที่เคยเป็นผลดีที่สุดของงานเป็น artifact ของคลัง 2018 เวอร์ชันเดิม

## 5. ข้อจำกัด

1. **ช่วงเวลาไม่เท่ากัน** ภายใน dataset เทียบกันห่างไม่กี่วัน แต่ข้าม dataset ห่างกันราว 8 เดือน ส่วนหนึ่งของช่องว่างอาจเป็นแค่เวลาที่ผ่านไปนานกว่า ข้อมูลชุดนี้ไม่มีทางแก้ข้อนี้ได้
2. **Bot ภายใน dataset ยังอธิบายไม่ได้** tree model ได้ 0.89 ถึง 0.94 เมื่อแบ่งหน้าต่างการโจมตี Bot ของปี 2017 ออกเป็นสองครึ่ง ยังไม่ทราบว่าเป็นเพราะ n เล็กหรือหน้าต่างนั้นมีสองช่วงจริง
3. **การวัดความต่างระหว่างวันแบบสะอาดมีแค่สองจุด** ทั้งคลัง 2018 มี sub-label เพียงสองตัวที่คร่อมมากกว่าหนึ่งวันโดยมีแถวพอ ส่วนคลัง 2017 ทุก sub-label อยู่ในไฟล์เดียว
4. **permutation importance มองไม่เห็นคอลัมน์ที่ซ้ำกัน** จึงรายงาน univariate ประกอบเสมอ
5. **กลไกของ RST Flag Count ยังไม่ได้ยืนยัน**
6. **Infiltration ทดสอบไม่ได้** เพราะฝั่ง 2017 มีเพียง 36 แถว
