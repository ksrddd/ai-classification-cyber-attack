# Cross-Dataset CICIDS2017 ↔ CSE-CIC-IDS2018 — สารบัญผลการทดลอง

รวมผลทุกรอบของงาน cross-dataset แยกตามรอบที่ทำ เพื่อให้ย้อนดูและเปรียบเทียบได้

แต่ละรอบแยกเป็นสามส่วนเหมือนกันหมด

```
roundN_ชื่อรอบ/
├── report/   รายงาน ทั้ง .md ที่แก้ได้ และ .pdf ที่ส่งได้
├── data/     ตารางผลดิบที่รายงานอ้างอิง
└── code/     สคริปต์ที่สร้างตารางนั้น (เฉพาะรอบที่มีสคริปต์เฉพาะกิจ)
```

**ทุกตัวเลขในโฟลเดอร์นี้มาจากไฟล์ผลลัพธ์จริง** แต่ละรอบเก็บทั้งรายงาน ข้อมูลดิบที่ใช้สร้าง
ตาราง และสคริปต์ที่รัน จึงตรวจย้อนกลับได้ทุกตัวเลข

## รอบ 1 — สรุปข้อเสนอแนะและ mapping

📁 `round1_advisor_plan/`

**คำถาม** ต้องทำอะไรบ้าง และสอง dataset เชื่อมกันได้อย่างไร

**ผลลัพธ์** mapping 77 shared features ระหว่างสอง dataset โดยจับคู่จากลำดับคอลัมน์ ไม่ใช่จาก
การเดาชื่อ พบว่า 27 คอลัมน์ชื่อตรงกันอยู่แล้ว 50 คอลัมน์ต้องแปลง ในนั้นมี 12 คอลัมน์ที่สลับ
ลำดับคำ และมีกับดักหนึ่งจุดคือ `CWE Flag Count` ที่ฝั่ง 2018 ลืมย่อ `Count` เป็น `Cnt`

**ยืนยันภายหลัง** mapping นี้ตรงกับ `feature_columns.json` และไฟล์ข้อมูลจริงของฝั่ง 2017
ทั้ง 77 ตัว เรียงตรงกันทุกตำแหน่ง

| ไฟล์ | เนื้อหา |
|---|---|
| `report/advisor_cross_dataset_summary.pdf` | สรุปข้อเสนอแนะ สถานะงาน และแผน |
| `data/shared_features_77.json` | ตารางแปลงชื่อคอลัมน์ ใช้ในโค้ดได้ทันที |

## รอบ 2 — ราคาของการย้ายไป shared schema (ภายในชุด 2018)

📁 `round2_schema_ablation_2018/`

**คำถาม** การเปลี่ยนไปใช้ schema ร่วมทำให้ผลเปลี่ยนไปเท่าไหร่ และเปลี่ยนเพราะอะไร

**วิธี** สี่เงื่อนไข เปลี่ยนทีละอย่าง บนตัวอย่าง 300k ของ 2018 split เดิม seed เดิม

| เงื่อนไข | feature | คลาส |
|---|---|---|
| A ฐานเดิม | 77 (มี Protocol) | 15 |
| B shared | 76 | 15 |
| B+ shared + Dst Port | 77 | 15 |
| C shared + ยุบคลาส | 76 | 7 |

**ผลสำคัญ** การยุบ 15 คลาสเหลือ 7 ทำให้ตัวเลขพาดหัวดีขึ้นแต่ประสิทธิภาพจริงแย่ลง

| lightgbm | macro ทุกคลาส | macro เฉพาะคลาสที่วัดได้ |
|---|---|---|
| ก่อนยุบ | 0.7126 | 0.8575 |
| หลังยุบ | **0.7880** | **0.8193** |

ตัวเลขสองชุดชี้คนละทิศ เพราะการยุบคลาสเอาคลาสที่ทำได้ดีไปรวมกับคลาสที่พัง และซ่อนคลาสจิ๋ว
ที่เคยได้ศูนย์ออกจากการนับ

ผลอื่น: ตัด `Protocol` ไม่มีราคาต้องจ่าย (สามในสี่โมเดลขยับไม่ถึง 0.002) และ `Destination Port`
ช่วย Infiltration จาก 0.1185 เป็น 0.1703

## รอบ 3 — Cross-dataset ครั้งแรก ด้วยโมเดลที่มีอยู่เดิม

📁 `round3_transfer_handoff_models/`

**คำถาม** ทำ cross-dataset ให้รันได้ก่อน ยังไม่เน้นผลดี

**วิธี** ใช้โมเดลที่เทรนไว้แล้วจากบันเดิล `cicids2017_temporal_v1` (เทรนด้วย 9 คลาส) ทำนาย
ข้อมูล 2018 แล้วยุบผลเป็น 7 คลาส ไม่ต้องใช้ข้อมูลดิบ 2017

**ผลสำคัญ** เทียบกับการเดาว่าทุกแถวเป็น Benign (macro-F1 0.1296)

| โมเดล | macro-F1 | กู้คืนได้ |
|---|---|---|
| stacking | 0.2428 | 20.3% |
| lightgbm | 0.2298 | 16.2% |
| random_forest | 0.1348 | **0.8%** |

random_forest ได้เท่าการเดาพอดี ส่วน mlp กับ logistic regression ได้ accuracy ต่ำกว่าการเดา

ตอนนั้นสรุปว่าสิ่งเดียวที่ถ่ายทอดได้คือความรู้เรื่อง traffic ปกติ (Benign 0.87–0.93) ส่วนคลาส
โจมตีพังเกือบหมด **ข้อสรุปนี้กว้างเกินไป** รอบ 4 พบว่าในทิศ 2018 ไป 2017 ซึ่งรอบ 3 วัดไม่ได้
นั้น Bot ทำได้ 0.94 และ Brute Force ทำได้ 0.91 ส่วนในทิศที่รอบ 3 วัด ข้อสรุปเดิมยังคงถูกต้อง

**การทดลองแทรก** บังคับให้โมเดลตอบได้แค่ 7 คลาสร่วม (ตัด probability ของ Heartbleed และ
PortScan ก่อน argmax) ดีขึ้นสูงสุด 0.008 และมีสองโมเดลแย่ลง จึงประเมินตอนนั้นว่าการทำคลาสให้
เท่ากันมีผลราว 1% — **การประเมินนี้วัดได้เพียงองค์ประกอบเดียว** และยังไม่มีรอบใดวัดผลรวมของ
การทำคลาสให้เท่ากันแบบแยกตัวแปรได้ ดูหัวข้อเทียบรอบ 3 กับรอบ 4

## รอบ 4 — Protocol เต็มรูปแบบ ⭐ รอบล่าสุด

📁 `round4_protocol_full/` · ผลดิบอยู่ที่ `results/crossdataset/protocol_v1/`

**คำถาม** ทำตาม protocol ให้ครบทุกข้อ แล้ววัดทั้งสี่ทิศทาง

**วิธี** 77 features · 7 คลาสเทรนตั้งแต่ต้น · 300k ต่อ dataset · 60/10/30 · 5 seeds ·
สองวิธีแบ่ง · 7 โมเดล · ไม่ทูน → 280 แถวผล

### ผลที่หนึ่ง — การแบ่งแบบสุ่มทำให้เพดานเฟ้อ และเฟ้อไม่เท่ากัน

| ชุด | เฟ้อขึ้นเท่าไหร่ |
|---|---|
| 2017 | **0.21 ถึง 0.32** |
| 2018 | 0.006 ถึง 0.033 |

ต่างกันสิบเท่า 2017 ภายใต้การแบ่งแบบสุ่มได้ 0.96–0.98 ซึ่งควรตั้งข้อสงสัยทันที

### ผลที่สอง — การถ่ายทอดไม่สมมาตร และวิธีแบ่งข้อมูลปิดบังข้อนี้ไว้

| วิธีแบ่ง | 2017→2018 | 2018→2017 |
|---|---|---|
| สุ่ม (ตาม protocol) | 31.1% | 25.8% |
| **ตามลำดับเวลา** | **7.5%** | **73.9%** |

ถ้ารันเฉพาะการแบ่งแบบสุ่มจะสรุปว่าสองทิศยากพอกัน ซึ่งไม่ตรงกับความจริง **วิธีแบ่งข้อมูล
เปลี่ยนข้อสรุป ไม่ใช่แค่เปลี่ยนตัวเลข**

### ผลที่สาม — ห้าในเจ็ดคลาสถ่ายทอดได้จริง

## เทียบรอบ 3 กับรอบ 4 ให้ถูกต้อง

รอบ 3 วัดได้ทิศเดียวคือ 2017 ไป 2018 ส่วนรอบ 4 วัดได้ทั้งสองทิศ **การเทียบต้องดูทิศเดียวกัน
เท่านั้น**

### ทิศ 2017 ไป 2018 ซึ่งเป็นทิศเดียวที่ทั้งสองรอบวัด — รอบ 4 ได้ต่ำกว่า

| โมเดล | รอบ 3 Brute Force | รอบ 4 Brute Force |
|---|---|---|
| stacking | 0.7359 | 0.0000 |
| xgboost | 0.3902 | 0.0000 |
| lightgbm | 0.2654 | 0.0000 |
| logistic_regression | 0.2394 | 0.0924 |

**แต่สรุปไม่ได้ว่ารอบ 4 แย่กว่า** เพราะเงื่อนไขต่างกันหลายอย่างพร้อมกัน

- รอบ 3 โมเดลเทรนด้วย 2017 ทั้ง corpus 1,748,579 แถว ส่วนรอบ 4 เทรนด้วย 180,000 แถว
- รอบ 3 ไม่ได้ clean ฝั่ง 2018 ส่วนรอบ 4 ตัดแถวซ้ำออก ทำให้ Brute Force ของ 2018 เหลือ 1,798 จาก 7,039 แถว
- วิธีแบ่งข้อมูลต่างกัน

### ตัวเลข 0.88 ถึง 0.91 เป็นของทิศ 2018 ไป 2017 ซึ่งรอบ 3 วัดไม่ได้

| โมเดล | Brute Force ทิศ 2018 ไป 2017 |
|---|---|
| mlp | 0.9145 |
| xgboost | 0.9017 |
| lightgbm | 0.8888 |
| stacking | 0.8831 |

**นี่คือของใหม่จริงของรอบ 4** ไม่ใช่การปรับปรุงตัวเลขเดิม

### เรื่องผลของการทำให้ชุดคลาสเท่ากัน — ยังไม่มีการวัดที่สะอาด

รอบ 3 ประเมินไว้ราว 1% จากการบังคับให้โมเดลตอบได้แค่ 7 คลาส ซึ่งวัดได้เพียงองค์ประกอบเดียว
คือคำทำนายที่เสียไปกับคลาสที่ไม่มีในเป้าหมาย

รอบ 4 เปลี่ยนหลายอย่างพร้อมกัน จึงแยกไม่ได้ว่าส่วนไหนมาจากการทำคลาสให้เท่ากัน **ทั้งสองรอบ
จึงยังไม่ได้ตอบคำถามนี้** ถ้าต้องการคำตอบต้องรันเงื่อนไขที่คุมทุกอย่างให้เหมือนกันแล้วเปลี่ยน
เฉพาะชุดคลาส

### สิ่งที่รอบ 4 เพิ่มขึ้นจริง

| ข้อ | รอบ 3 | รอบ 4 |
|---|---|---|
| ทิศทางที่วัดได้ | 1 | **4 combination** |
| Seeds | 1 | **5 พร้อมค่าเบี่ยงเบน** |
| วิธีแบ่งข้อมูล | 1 | **2 และพบว่ามันเปลี่ยนข้อสรุป** |
| การ clean | ไม่ได้ทำ | **กฎเดียวกันสองฝั่ง** |
| ที่มาของโมเดล | ของผู้อื่น ยืนยันไม่ได้ | **เทรนเองทั้งหมด** |

## สองคลาสที่ไม่ถ่ายทอดในทุกรอบ

`Infiltration` และ `Web Attack` ได้ F1 เท่ากับศูนย์ในทุกรอบ ทุกทิศ ทุกโมเดล ทุก seed ด้วย
เหตุผลคนละแบบ

| คลาส | 2017 | 2018 | สาเหตุ |
|---|---|---|---|
| Web Attack | 2,143 | **17** | ข้อมูลไม่พอ ฝั่งหนึ่งแทบไม่มีเลย |
| Infiltration | **36** | 2,946 | ข้อมูลไม่พอ **และ** label เสีย |

Infiltration หนักกว่า เพราะแม้ทิศที่มีข้อมูลเทรน 1,700 แถวก็ยังได้ศูนย์ และแม้แต่ตอนเทรนกับ
ทดสอบภายในชุดเดียวกันยังได้เพียง 0.05–0.13 ในทุกโมเดล

## ข้อจำกัดที่ยังเหลือ

1. ฝั่ง 2018 หลัง clean เหลือ 262,701 แถว ไม่ครบ 300,000 ตาม protocol แก้ได้โดยโหลดจาก `sample_500k.parquet` แทน ซึ่งทดสอบแล้วได้ครบ 300,000 พอดี
2. ช่อง calibration 10% กันไว้แล้วแต่ยังไม่ได้ใช้
3. ยังไม่ได้ทูน hyperparameter
4. ยังไม่ได้ทำ adversarial validation
5. ตัวบอกลำดับเวลาต่างกัน 2017 ใช้ลำดับแถวในไฟล์ 2018 ใช้ timestamp จริง
