# สรุปข้อเสนอแนะจากอาจารย์ และแผนงาน Cross-Dataset

เอกสารนี้รวบรวมทุกอย่างที่อาจารย์แนะนำมาระหว่างวันที่ 6 ถึง 8 สิงหาคม 2569 พร้อมสถานะงาน
ฝั่งเรา และแผนการเปรียบเทียบผลเก่ากับผลใหม่

ทุกตัวเลขในเอกสารนี้ดึงมาจากไฟล์ผลลัพธ์จริงในโปรเจกต์ ไม่มีการประมาณการ

## 1. สรุปสั้น

อาจารย์ทดลอง cross-dataset ระหว่าง CICIDS2017 กับ CSE-CIC-IDS2018 ทั้งสองทิศแล้ว พบว่า
ผลไม่ดีทั้งคู่ และวิธีแก้สามอย่างที่ลองไปก็ไม่ช่วย จึงสรุปว่าการทำ generalisation ข้ามชุด
ข้อมูลน่าจะยากมาก แล้วขอให้เราวางแผนของตัวเองมาเสนอ

แผนที่เราเสนอคือไม่ไปแข่งทำให้ cross-dataset เวิร์ค แต่แยกให้ได้ว่าช่องว่างของผลลัพธ์
ประกอบด้วยอะไรบ้าง และแต่ละส่วนกินสัดส่วนเท่าไหร่ เพราะข้อมูลที่เรามีอยู่ชี้ว่าส่วนหนึ่ง
ของปัญหาไม่ได้อยู่ที่โมเดล แต่อยู่ที่คุณภาพของชุดข้อมูลเอง

ล่าสุดอาจารย์ขอผลเบื้องต้นก่อน โดยระบุว่าไม่ต้องได้ผลดี ขอแค่ให้รันข้ามชุดข้อมูลได้

## 2. สิ่งที่อาจารย์แนะนำมาทั้งหมด

### 2.1 วันที่ 6 สิงหาคม เวลา 12:04

- ให้ตรวจสอบเรื่อง tuning ของแต่ละโมเดล เพราะสงสัยว่าบางโมเดลของเราไม่แฟร์
- แจ้งว่าลอง cross-dataset แล้วทั้งสองทิศ คือเทรนด้วย 2017 ทดสอบกับ 2018 และเทรนด้วย 2018 ทดสอบกับ 2017 ผลไม่ดีทั้งคู่
- ตอนนั้นใช้ข้อมูล 7 คลาส จำนวนสามแสนแถว
- ขอให้เราไปวางแผนของตัวเองมาว่าจะไปทางไหน

### 2.2 วันที่ 6 สิงหาคม เวลา 12:13

แจ้งว่าลองหลายวิธีแล้วไม่ช่วยให้ดีขึ้น บางวิธีแย่ลงด้วยซ้ำ วิธีที่ลองไปแล้วมีสามอย่าง

1. ลดปัญหาจาก multiclass ให้เหลือ binary
2. ลบ features ที่บ่งบอกว่า record มาจาก dataset ไหน
3. Distribution alignment

### 2.3 วันที่ 8 สิงหาคม เวลา 16:55

- ชื่อฟิลด์ระหว่าง 2017 กับ 2018 ไม่เหมือนกัน ต้องทำ mapping เอง
- ในข้อมูลจะมีค่าแปลก ๆ ต้องทำความสะอาดเอง

### 2.4 ข้อความล่าสุด

ขอผลเบื้องต้น ไม่จำเป็นต้องได้ผลดี ขอแค่ให้ cross-dataset รันได้ก่อน

## 3. Protocol ข้อมูลที่อาจารย์กำหนด

| หัวข้อ | ค่าที่กำหนด |
|---|---|
| การทำความสะอาด | แยกทำทีละชุด แก้ชื่อคอลัมน์ แก้ชนิดข้อมูล ตัดค่าที่ใช้ไม่ได้ |
| จำนวนคลาส | 7 classes ที่มีร่วมกัน |

## 4. สถานะงานเทียบกับที่อาจารย์ขอ

| สิ่งที่อาจารย์ขอ | สถานะ |
|---|---|
| ตรวจ tuning ว่าแฟร์หรือไม่ | เสร็จแล้ว |
| ส่งแผนของตัวเอง | ตอบไปบางส่วนทางแชท ยังไม่ได้ส่งเป็นก้อน |
| ทำ mapping ชื่อฟิลด์เอง | เสร็จแล้ว ยังไม่ได้ย้ายเข้าโปรเจกต์ |
| ทำความสะอาดข้อมูลเอง | สำรวจแล้วว่ามีปัญหาอะไรบ้าง ยังไม่ได้เขียน cleaner |
| ยุบเหลือ 7 classes | ยังไม่เริ่ม |

| ทำซ้ำ 5 seeds | ยังเป็น 1 seed |
| ลด multiclass เหลือ binary | มีเฉพาะฝั่ง 2017 ฝั่ง 2018 ยังไม่มี |
| ลบ features ที่บ่งบอก dataset | ยังไม่เริ่ม |
| Distribution alignment | อาจารย์ทำเอง เราไม่แตะ |
| ให้ cross-dataset รันได้ | ยังทำไม่ได้ ติดที่ไม่มีข้อมูล 2017 |

## 5. งานที่เสร็จแล้ว การตรวจสอบ tuning

อาจารย์สงสัยถูกต้อง ระบบเดิมให้ทุกโมเดลค้นหา 20 ชุดพารามิเตอร์เท่ากัน แต่ขนาด search
space ของแต่ละโมเดลต่างกันมาก ตั้งแต่ 10 ถึง 5,184 ชุด ผลคือ logistic regression ได้
ค้นหาครบทุกความเป็นไปได้ ในขณะที่ xgboost ได้ค้นเพียงเศษเสี้ยว

แก้ไขโดยปรับ search space ของทั้งหกโมเดลให้เท่ากันที่ 144 ชุด แล้วรันใหม่ทั้งหมดลง
bundle ชื่อ `300k_temporal_tuned_fair` และ `500k_temporal_tuned_fair`

ผลของการรันใหม่ให้ข้อสรุปที่สำคัญกว่าตัวการแก้บั๊กเสียอีก คืออันดับของโมเดลเปลี่ยนไป 10
จาก 14 ตำแหน่ง แต่คะแนนบนคลาสที่วัดผลได้จริงไม่มีโมเดลไหนขยับเกิน 0.007 แปลว่าอันดับที่
เห็นก่อนหน้านี้สะท้อนโชคในการค้นหาพารามิเตอร์บนคลาสหายาก มากกว่าจะสะท้อนคุณภาพของโมเดล

## 6. Mapping ที่ทำเสร็จแล้ว

ใช้ชื่อคอลัมน์ฝั่ง 2017 เป็นชื่อกลาง แล้วแปลงชื่อฝั่ง 2018 เข้ามาหา

### 6.1 คอลัมน์ที่ตัดออกก่อนจับคู่

| ฝั่ง | ตัดออก | เหตุผล |
|---|---|---|
| 2017 | `Fwd Header Length.1` | คอลัมน์ซ้ำ เป็นบั๊กของไฟล์ต้นฉบับ |
| 2018 | `Flow ID` `Src IP` `Src Port` `Dst IP` | เป็นข้อมูลระบุตัวตน ไม่ใช่ feature |
| 2018 | `Protocol` `Timestamp` | ฝั่ง 2017 ไม่มีในรายการ feature |

หลังตัดแล้วเหลือ 77 ตรงกับ 77 พอดี ซึ่งตรงกับจำนวนที่อาจารย์ระบุไว้

### 6.2 วิธีจับคู่

ไม่ได้จับคู่จากการเดาชื่อ แต่เรียงคอลัมน์ตามลำดับเดิมของทั้งสองไฟล์แล้วจับคู่ตามตำแหน่ง
พบว่าเรียงตรงกันทุกตำแหน่งโดยไม่มีการสลับเลย ซึ่งสมเหตุสมผลเพราะทั้งสองชุดถูกสกัด feature
ด้วย CICFlowMeter เหมือนกัน ต่างกันแค่เวอร์ชัน

ผลการจับคู่คือ 27 คอลัมน์ที่ชื่อเหมือนกันอยู่แล้ว และ 50 คอลัมน์ที่ต้องแปลงชื่อ

### 6.3 คอลัมน์ที่สลับลำดับคำ ต้องระวังเป็นพิเศษ

ส่วนใหญ่ของ 50 คอลัมน์เป็นการย่อคำตรงไปตรงมา แต่มี 12 คอลัมน์ที่สลับลำดับคำด้วย ถ้าเขียน
กฎแปลงชื่ออัตโนมัติจะพลาดกลุ่มนี้ทั้งหมด

|---|---|
| `Min Packet Length` | `Pkt Len Min` |
| `Max Packet Length` | `Pkt Len Max` |
| `Average Packet Size` | `Pkt Size Avg` |
| `Avg Fwd Segment Size` | `Fwd Seg Size Avg` |
| `Avg Bwd Segment Size` | `Bwd Seg Size Avg` |
| `Fwd Avg Bytes/Bulk` | `Fwd Byts/b Avg` |
| `Fwd Avg Packets/Bulk` | `Fwd Pkts/b Avg` |
| `Fwd Avg Bulk Rate` | `Fwd Blk Rate Avg` |

สามแถวล่างหนักที่สุด เพราะฝั่ง 2017 ใช้ snake_case และวางทิศทางไว้ท้ายชื่อ ส่วนฝั่ง 2018
ใช้ Title Case และวางทิศทางไว้หน้าชื่อ

นอกจากนี้ยังมีกับดักอีกหนึ่งจุด คือฝั่ง 2018 ย่อคำว่า Count เป็น Cnt ทุกตัว ยกเว้น
`CWE Flag Count` ที่ลืมย่อ ถ้าเขียนกฎแปลงแบบเหมารวมจะพังตรงจุดนี้

## 8. แผนเปรียบเทียบผลเก่ากับผลใหม่

หลังทำ mapping แล้วจะเทียบผลเก่ากับผลใหม่ตรง ๆ ไม่ได้ เพราะเปลี่ยนไปพร้อมกันหลายอย่าง คือ
จำนวน feature ลดจาก 79 เหลือ 77 และจำนวนคลาสยุบจาก 15 เหลือ 7 สองอย่างนี้ดันคะแนนคนละทิศ
ถ้ารันทีเดียวแล้วเทียบจะแยกไม่ออกว่าอะไรทำให้ผลเปลี่ยน

จึงต้องไล่ทีละขั้น เปลี่ยนทีละอย่าง

| ขั้น | เงื่อนไข | ตอบคำถามว่า |
|---|---|---|
| A | 79 feature และ 15 คลาส | ฐานอ้างอิง มีผลอยู่แล้ว |
| B | 77 feature และ 15 คลาส | การตัด Protocol กับ Timestamp มีราคาเท่าไหร่ |
| C | 77 feature และ 7 คลาส | การยุบคลาสซื้อคะแนนมาเท่าไหร่ |
| D | เงื่อนไข C แต่ข้ามชุดข้อมูล | การข้ามชุดข้อมูลมีราคาเท่าไหร่ |

ส่วนต่างระหว่างขั้น D กับขั้น C คือราคาที่แท้จริงของการข้ามชุดข้อมูล ส่วนต่าง B ลบ A และ
C ลบ B เป็นราคาของการปรับ schema ซึ่งไม่ควรนำไปปนกัน

ขั้น B และ C รันได้ทันทีโดยไม่ต้องรอข้อมูล 2017 เพราะใช้ตัวอย่าง 300,000 แถวของ 2018 ที่
มีอยู่แล้ว และใช้ split เดิม seed เดิม ขณะเขียนเอกสารนี้ยังไม่ได้รัน ตัวเลขในหัวข้อ 9 จึง
เป็นฝั่งของเก่าอย่างเดียว

## 9. ผลเก่าที่จะใช้เป็นฐานเปรียบเทียบ

bundle ที่ควรใช้เป็นฐานคือ `results/ids2018/300k_temporal_tuned_fair` เพราะเป็นตัวเดียวที่
ทูนแบบแฟร์แล้ว ตั้งค่าคือ 300,000 แถว seed 42 แบ่ง 70/30 แบบ temporal จำนวน 15 คลาส

### 9.2 bundle `300k` random split ไม่ทูน

เพื่อสรุปว่า temporal split ยากกว่าหรือง่ายกว่า ต้องรันเงื่อนไขที่คุมตัวแปรอื่นให้เท่ากัน
ก่อนจึงจะสรุปได้ ซึ่งเป็นเหตุผลเดียวกับที่ต้องไล่ขั้น A ถึง D ในหัวข้อ 8

## 10. หลักฐานที่สนับสนุนแผน

### 10.1 บางคลาสตันเท่ากันทุกโมเดล

จากไฟล์ `per_class_f1_matrix.csv` ของ bundle 500k ที่ทูนแฟร์แล้ว มีคลาสที่ทุกโมเดลได้คะแนน
ใกล้เคียงกันหมด ตั้งแต่ logistic regression ไปจนถึง catboost

| คลาสของ 2018 | ช่วง F1 จาก 7 โมเดล |
|---|---|
| Infilteration | 0.00 ถึง 0.13 |
| DoS attacks-SlowHTTPTest | 0.619 ถึง 0.638 |
| FTP-BruteForce | 0.755 ถึง 0.800 |

ฝั่ง 2017 ก็มีอาการเดียวกัน คลาส Bot มีค่า recall อยู่ระหว่าง 0.150 ถึง 0.161 เหมือนกันทั้ง
เจ็ดโมเดล

เมื่อโมเดลเชิงเส้นกับ gradient boosting ที่ทูนแล้วได้ผลเท่ากัน แปลว่าเพดานนั้นไม่ได้อยู่ที่
โมเดล แต่อยู่ที่ข้อมูล ถ้าช่องว่างของ cross-dataset ส่วนใหญ่มาจากสาเหตุนี้ distribution
alignment ก็แก้ไม่ได้ ซึ่งอาจอธิบายได้ว่าทำไมสามวิธีที่อาจารย์ลองจึงไม่ขึ้น

### 10.2 คลาสที่มี test flow น้อยเกินกว่าจะวัดผลได้

ที่ขนาดตัวอย่าง 500,000 แถว มีสี่คลาสที่มี test flow รวมกันเพียง 25 แถวจาก 150,011 แถว ได้แก่
`SQL Injection` 1 แถว `Brute Force -XSS` 2 แถว `Brute Force -Web` 6 แถว และ
`DDOS attack-LOIC-UDP` 16 แถว แต่ละคลาสถือน้ำหนักหนึ่งในสิบห้าของ macro-F1 เท่ากับคลาส Benign
ที่มี 124,610 แถว

ผลคือช่วงความเชื่อมั่นของ macro-F1 ที่ขนาด 300k กว้างเฉลี่ยประมาณ 0.128 และการเพิ่มข้อมูลจาก
300k เป็น 500k ไม่ได้ทำให้แคบลงเลย เพราะความกว้างมาจากคลาสที่หายากที่สุด ไม่ได้มาจากขนาดข้อมูลรวม

ข้อนี้มีผลต่อการอ่านผลขั้น C ในหัวข้อ 8 โดยตรง การยุบเหลือ 7 คลาสจะทำให้ Web Attack ดูดสาม
ในสี่คลาสนี้เข้าไป และ DoS ดูด SlowHTTPTest ที่พังอยู่เข้าไป คะแนนจะกระโดดขึ้นอย่างเห็นได้ชัด
แต่ไม่ได้แปลว่าโมเดลเก่งขึ้น ต้องเขียนกำกับไว้เสมอ

## 11. การยุบ 15 คลาสเหลือ 7 คลาส

คลาสที่มีร่วมกันเจ็ดคลาสคือ Benign, Bot, Infiltration, DDoS, DoS, Brute Force และ Web Attack

สามคลาสแรกจับคู่หนึ่งต่อหนึ่ง โดย Infiltration ฝั่ง 2018 สะกดว่า Infilteration ส่วนอีกสี่คลาส
ต้องยุบหลายคลาสของ 2018 เข้าด้วยกัน คลาส Heartbleed และ PortScan ของ 2017 ไม่มีคู่ในฝั่ง 2018
จึงต้องตัดออก

## 12. สิ่งที่ต้องทำต่อ

### 12.1 รอบนี้ ให้ cross-dataset รันได้ก่อนตามที่อาจารย์ขอ

1. ย้าย mapping 77 features เข้าโปรเจกต์เป็นโมดูลจริง พร้อม test กันชื่อคอลัมน์เปลี่ยน
2. เขียน label mapping 7 คลาสร่วม
3. เขียน cleaner ที่ทั้งสองชุดใช้กฎเดียวกัน
4. สุ่มตัวอย่าง 300,000 แถวจาก 2017 ด้วยวิธีเดียวกับที่ทำกับ 2018
5. รัน 2017 ไป 2018 และ 2018 ไป 2017 แบบไม่ทูน หนึ่งโมเดล หนึ่ง seed

### 12.2 รอบถัดไป ทำให้ครบ protocol

1. เปิดช่อง calibration 10% และรันครบ 5 seeds
2. เพิ่มโหมด binary ฝั่ง 2018 ให้เท่ากับฝั่ง 2017
3. ทำ adversarial validation เพื่อหา feature ที่บ่งบอก dataset
4. เพิ่มเงื่อนไข temporal split ควบคู่กับ random split

## 13. ตัวติดขัดและคำถามที่ยังค้าง

ตัวติดขัดเดียวที่ทำให้เริ่มไม่ได้คือไม่มีข้อมูลดิบของ CICIDS2017 อยู่ในเครื่อง โฟลเดอร์
`data/raw` `data/processed` และ `data/interim` ว่างทั้งหมด มีเพียงไฟล์ตัวอย่างของ 2018 สองไฟล์
งานข้อ 3 ถึง 5 ในหัวข้อ 12.1 ขยับไม่ได้จนกว่าจะมีไฟล์ชุดนี้

คำถามที่ยังไม่ได้คำตอบจากอาจารย์

1. เป้าหมายของงานคือต้องได้ผลที่ดีขึ้นจริง หรือได้ข้อสรุปที่อธิบายได้ก็เพียงพอ
2. ขอรายชื่อ 7 คลาสและ 77 features ที่อาจารย์ใช้จริง พร้อม seed ที่ใช้ เพื่อให้ตัวเลขของสองฝั่งเทียบกันได้
3. ขอตัวเลข baseline ของอาจารย์ทั้งสองทิศไว้ตรวจสอบว่าฝั่งเรารันถูกทาง
4. protocol ที่ให้มาใช้การสุ่มแบ่ง 60/10/30 ซึ่งทำให้ flow จากช่วงเวลาโจมตีเดียวกันไปอยู่ทั้งฝั่ง train และ test ขออนุญาตรันเงื่อนไข temporal split ควบคู่ไปด้วย
